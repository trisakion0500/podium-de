## 배포와 아키텍처

### <a id="d-01"></a>D-01. 싱글테넌트, 프로젝트별 독립 배포 — 확정

**결정:** 게임 프로젝트마다 별도 인스턴스와 DB를 배포한다. (Dedicated Edition)

**배경:** 여러 프로젝트를 받는 SaaS 형태를 검토했다.

**검토한 대안**
- 멀티테넌트 공유 테이블 (`project_id`로 구분)
- 테넌트별 스키마 + 컨트롤 플레인

**이유**
- 공유 테이블은 프로젝트마다 시즌 일정이 달라 시즌 단위 파티션이 성립하지 않고, `(project_id, season)` 파티션은 개수 상한(8192)에 닿는다.
- EXCHANGE의 MDL이 테이블 전체에 걸려 한 프로젝트의 정산이 다른 프로젝트의 쓰기를 멈춘다.
- 대형 프로젝트의 부하가 다른 프로젝트에 영향을 준다(노이지 네이버).
- 독립 배포는 위 문제가 구조적으로 사라지고, 랭킹 설계에서 테넌트 식별자가 필요 없다.

**감수할 것:** 설치본 간 버전 차이, 마이그레이션 N회 실행, 소규모 프로젝트의 인프라 비용.

### <a id="d-02"></a>D-02. MySQL 원장, Redis 투영 — 확정

**결정:** 스코어는 MySQL에 먼저 적재하고, 확정된 값을 Redis에 반영한다.

**검토한 대안**
- Redis 단독 (AOF + 레플리카)
- Redis 우선 + write-behind로 MySQL 적재

**이유**
- 보상이 걸린 랭킹은 기록 하나의 유실이 CS 사고가 된다.
- 정산, 검수, 어뷰징 조사에는 감사 가능한 원장이 필요하다.
- Redis 값이 MySQL 행에서 결정적으로 계산되므로, 복구가 "다시 계산해서 넣기"로 단순해진다.
- 싱글테넌트라 설치본당 쓰기량이 제한적이다. DAU 100만, 1인 20회 제출 기준 평균 약 230건/초, 피크 약 2,300건/초로 MySQL이 감당 가능한 범위로 추정한다. 부하 테스트에서 커밋마다 fsync하는 설정으로 3,000건/초까지 행 잠금 대기 없이 처리했다(로컬 단일 장비, [06_LOAD_TEST](06_LOAD_TEST.md)). 목표 규모는 D-61에서 MAU 100만으로 정했다. 위 추정은 그 목표에 대한 여유의 근거로 남긴다.

**참고:** 보상이 없는 표시 전용 랭킹이라면 Redis 단독도 타당하다.

### <a id="d-03"></a>D-03. 달성 시각은 MySQL이 기록 — 확정

**결정:** `achieved_at`은 MySQL 마스터의 `NOW(3)`으로 기록한다.

**변경 이력:** 처음에는 Redis Lua 안에서 `TIME`으로 기록하는 안이었다. ([D-02](#d-02) 이전)

**이유:** MySQL이 원장이 되면서 시각도 원장에 있어야 재구축 시 같은 composite를 재현할 수 있다. 시계가 하나라 서버 간 시간 차이로 순서가 뒤집히지 않는다.

### <a id="d-04"></a>D-04. Redis 영속화는 RDB 기본, AOF 미사용 — 확정

**이유:** MySQL이 원장이라 Redis 유실은 정합성 문제가 아니다. 영속화는 재시작 후 재구축 시간을 줄이는 용도뿐이다. 스냅샷 이후 유실분은 리컨실러가 메운다(센티넬 값부터 다시 읽는다, [01_DESIGN 6.2](01_DESIGN.md#s-6-2)). AOF는 쓰기 IO 비용에 비해 이득이 작다. 소규모 설치본은 영속화를 끌 수 있게 설정으로 연다.

## 순위 규칙

### <a id="d-05"></a>D-05. 동점은 composite score 인코딩으로 처리 — 확정

**결정:** `score × 2^T + 시간 성분`으로 하나의 ZSET score에 점수와 달성 시각을 함께 넣는다. 비트 배분은 랭킹 등록 시 결정한다.

**이유**
- 조회 시 별도 정렬 없이 Redis 순서가 곧 순위다.
- 동점이 시간으로 모두 갈려 순위가 고유하다.
- BEST 규칙은 `ZADD GT`(ASC는 `LT`)만으로 "같은 점수는 먼저 달성한 쪽 유지"까지 자동으로 보장된다.

**감수할 것:** double 정밀도(2^53) 안에서 점수 범위와 시간 범위가 교환 관계다. 등록 시 검증으로 막는다.

### <a id="d-06"></a>D-06. 갱신 규칙 BEST / SUM / LATEST — 확정 (LATEST는 보류)

**결정:** 등록 시 규칙을 선택한다. 1차는 BEST, SUM. LATEST는 코드만 정의하고 등록을 막는다.

**이유**
- 스코어를 의미 없는 정수로 다루면, 규칙과 정렬 방향의 조합으로 타임어택, 누적 포인트, 최고 기록을 모두 표현할 수 있다.
- 전투력, 레벨처럼 게임 서버가 계산한 현재 값을 겨루는 랭킹은 BEST나 SUM으로 표현할 수 없어 LATEST가 필요하다.

### <a id="d-07"></a>D-07. 감소하는 점수는 SUM의 부호 있는 증분으로 — 확정

**결정:** 점수가 깎이는 랭킹은 SUM에 음수 증분을 허용하고 하한 0으로 처리한다. `GREATEST(score + delta, 0)`

**검토한 대안**
- LATEST(절대값)로 받기
- 양수는 `GT` 경로, 음수는 version 경로로 분기

**이유**
- LATEST는 게임 서버 쪽 요청 순서가 뒤집히면 오래된 값이 최신 값을 덮어쓴다. 계산을 MySQL 행 락 안에서 하는 증분 방식이 동시성에 안전하다.
- 경로를 분기하면 `GT` 경로가 version HASH를 갱신하지 않아 비교가 틀어진다. SUM은 항상 version 경로로 통일한다.

**부가 결정:** 값이 실제로 바뀌지 않으면(0점에서 음수 증분) version과 달성 시각을 갱신하지 않는다. 동점 순서가 이유 없이 밀리는 것을 막는다.

### <a id="d-08"></a>D-08. LATEST는 소스 시퀀스 비교 — 보류

**결정:** 게임 서버가 현재 값과 소스 시퀀스를 함께 보내고, SP는 시퀀스가 클 때만 덮어쓴다.

**이유:** 도착 순서가 곧 결과가 되는 규칙이라, 순서 보장 장치 없이는 오래된 값이 최신 값을 덮어쓴다.

### <a id="d-09"></a>D-09. 영구 랭킹은 큰 시간 단위 허용 — 확정

**결정:** `time_unit`에 MIN, DAY를 허용하고, 영구 랭킹은 최소 30년을 커버하도록 검증한다.

**이유:** 영구 랭킹은 시즌 길이 상한이 없어 SEC 단위로는 점수 비트가 부족해진다. 영구 랭킹에서 초 단위 동점 판정의 의미는 작다.

## 시즌과 정산

### <a id="d-10"></a>D-10. 파티션은 LIST COLUMNS(ranking_id, season_no) — 확정

**변경 이력:** RANGE COLUMNS로 검토했다가 변경했다.

**이유**
- RANGE는 경계 사이 공백이 없어, 랭킹 1의 다음 시즌 데이터가 랭킹 2의 파티션 범위로 들어갈 수 있다. 막으려면 랭킹마다 빈 future 파티션과 REORGANIZE가 필요하다.
- LIST는 순서 제약이 없어 `ADD PARTITION`만으로 어떤 시즌이든 추가할 수 있다.
- 정의되지 않은 쌍은 INSERT 에러가 나서, 잘못된 파티션에 조용히 들어가는 것보다 안전하다.

### <a id="d-11"></a>D-11. 쓰기 차단은 시각 검사로 — 확정

**결정:** SP가 `NOW(3)`이 `[start_at, end_at)` 안인지 직접 검사한다. 상태 전이는 기록용이다.

**이유:** 종료 순간 상태를 바꾸는 잡이 늦게 돌아도 마감이 뚫리지 않는다. 자가 복구 원칙과 일치한다.

### <a id="d-12"></a>D-12. 시즌 기간 / 정산 유예 / 대기 기간 — 확정

**결정:** 정의에 세 기간을 둔다. 정산은 시즌 사이에 직렬로 끼우지 않고 다음 시즌과 병렬로 진행한다.

**이유:** 정산을 직렬로 두면 로테이션 랭킹에 정산 시간만큼 빈 구간이 생긴다.

**변경 이력:** 대기 기간은 처음에 단일 시즌의 보상 수령 기간 역할도 했으나, [D-15](#d-15) 이후 순수한 시즌 간 휴식 의미만 남았다.

### <a id="d-13"></a>D-13. 정산 유예는 시각 하한 + 실제 종료 검증 — 확정

**결정:** `end_at + settle_delay` 이후, `INNODB_TRX`에 종료 전 시작된 트랜잭션이 없고 리컨실러가 따라잡았을 때 정산을 시작한다.

**이유:** 시각 검사를 통과해 이미 처리 중인 요청의 커밋이 종료 후에 끝날 수 있다. 유예 시간은 하한이고, 실제 시작은 시스템이 닫힘을 확인한 뒤다.

### <a id="d-14"></a>D-14. 늦은 제출은 엄격 마감 — 확정 (허용 옵션은 보류, D-30으로 보완)

**결정:** `end_at` 이후 제출은 전부 거부한다.

**검토한 대안:** 게임 서버가 전투 시작 시각을 보내고, 시즌 안에서 시작한 건은 유예 시간까지 받는 방식.

**이유:** 대부분의 게임이 엄격 마감이며 공정성 시비가 없다. 허용 방식은 게임 서버가 보낸 시작 시각을 신뢰해야 한다. 긴 전투(레이드 등)를 지원할 때 `late_submit_grace` 옵션으로 추가한다.

### <a id="d-15"></a>D-15. 보상은 수령형이 아니라 일괄 전달 — 확정

**결정:** 정산 시 대상자 보상을 확정하고, 게임 서버가 목록을 페이지 단위로 가져가 ack하는 방식으로 전달한다. 수령 기간은 랭킹 서버에 두지 않는다.

**변경 이력**
1. 수령 기간(`claim_period`)을 두는 수령형 → 접은 유저 때문에 데이터를 정리할 수 없다는 우려
2. 직전 시즌만 수령 가능, 다음 시즌 정산 시 만료 (포인터 방식)
3. 수령 마감 = 종료(N) + 대기 기간 + 다음 시즌 기간 (시각 방식)
4. **일괄 전달로 최종 변경**

**이유**
- 수령 대기 상태 자체가 사라져 결과 데이터의 보존 기간이 짧아진다.
- 접은 유저 문제는 게임 서버 우편 만료로 넘어간다.
- 게임 서버가 자기 속도로 가져가 부하 조절이 쉽고, 지급 멱등 키로 중복 지급이 없다.

**원칙 확인:** 데이터 이동 조건에 유저 행동(수령 여부)을 넣지 않는다. 전달이 장기간 멈추면 그것은 연동 장애로 보고 알림을 보낸다.

### <a id="d-16"></a>D-16. 지급 전 검수 단계 — 확정

**결정:** 가순위 생성 → 검수 → 확정 → 전달 순서로 정산을 나눈다. 검수 기간은 시각으로 자동 종료하고, GM은 보류와 조기 확정만 할 수 있다.

**배경:** 2등이 어뷰저로 확인되었을 때, 3등이 이미 보상을 받은 뒤라면 정상 유저의 보상을 회수하고 재지급해야 한다.

**이유**
- 지급 전에 제재를 반영하고 순위를 다시 매기면 정상 유저가 피해를 보지 않는다.
- GM 승인을 기다리는 구조는 사람 손 없이 진행되어야 한다는 원칙에 어긋난다.

**부가 결정:** 확정 이후 순위는 다시 매기지 않는다. 지급 후 적발은 순위를 유지하고 어뷰저의 보상만 게임 서버가 회수한다.

### <a id="d-17"></a>D-17. 보상 상태와 제재 표시 분리 — 확정

**결정:** `reward_status`(NONE / PENDING / DELIVERED / REJECTED)와 `sanctioned` 플래그를 별도 컬럼으로 둔다.

**이유**
- "대상 아님"과 "제재로 거부"는 결과가 같아도 CS 대응에서 구분되어야 한다.
- 지급 후 적발은 보상 상태는 DELIVERED인데 제재 표시가 필요하다. 한 컬럼으로는 경우의 수가 꼬인다.
- 제재 유저의 표시 방식은 게임마다 다르므로 랭킹 서버는 플래그만 제공한다.

## 아카이브

### <a id="d-18"></a>D-18. EXCHANGE 1회 + 시즌별 일반 테이블 — 확정

**결정:** 운영 테이블의 시즌 파티션을 일반 테이블과 한 번 EXCHANGE하고, 그 테이블을 그대로 백업으로 사용한다.

**변경 이력**
1. 최초 안: `rank` 파티션 → `rank_archive` 파티션으로 이동 → 히스토리 테이블로 배치 복사 → `rank_archive` 파티션 삭제
2. 파티션 ↔ 파티션 직접 EXCHANGE가 불가능함을 확인하고, 중간 일반 테이블을 경유하는 2단 EXCHANGE로 수정
3. 2단 EXCHANGE 대신 정산 끝난 파티션에서 직접 복사 후 DROP 하는 안 검토
4. **EXCHANGE 1회 + 시즌별 일반 테이블로 최종 확정**

**이유**
- EXCHANGE의 가치는 운영 테이블에서 무거운 삭제를 빼내는 것이다. 데이터가 찬 파티션을 직접 DROP하면 배타 MDL을 잡은 채 파일 삭제가 진행되어 모든 랭킹의 쓰기가 멈출 수 있다. (3번 기각 이유)
- 두 번째 EXCHANGE는 같은 인스턴스, 디스크, 버퍼 풀 안에서 일어나므로 추가로 얻는 것이 없다. 대가로 테이블 하나, 스키마 동기화, 파티션 경계값 관리가 따라온다. (2번 기각 이유)
- EXCHANGE 후 일반 테이블이 곧 보관본이므로 데이터 복사가 한 번도 없다.

**확인된 사실:** EXCHANGE 대상은 반드시 비파티션 테이블이며, 교환 후에도 일반 테이블이다. 교환되는 것은 데이터 파일이다.

### <a id="d-19"></a>D-19. 보관본은 파티션 히스토리가 아닌 시즌별 테이블 — 확정

**검토한 대안:** 히스토리 자체를 LIST COLUMNS 파티션 테이블로 두고 두 번째 EXCHANGE로 복사 없이 보관.

**이유**
- 파티션 수가 늘면 테이블 오픈, 메타데이터 처리, DDL이 무거워지고 상한(8192)이 있다.
- 히스토리 스키마 변경이 과거 시즌 전체에 걸린다.
- 시즌별 테이블은 시즌 단위로 독립 삭제, 덤프, 이동이 가능하다.

**감수할 것:** 테이블 수 증가. `history_retention`이 지난 테이블을 경고하고(삭제는 운영자, [01_DESIGN 8.3](01_DESIGN.md#s-8-3)) 캐시 관련 설정을 맞춘다. 여러 시즌 교차 조회가 어렵지만 D-23으로 해소한다.

### <a id="d-20"></a>D-20. entry 분리 시점은 SETTLING — 대체됨 (D-49)

**결정:** 정산 시작 시 entry 파티션을 분리하고, 그 데이터로 result를 생성한다.

**변경 이력:** 처음에는 검수 재계산을 위해 SETTLED까지 entry를 운영 테이블에 유지하는 안이었다.

**이유**
- 검수 단계의 순위 재부여는 result만으로 가능하다.
- 원본 조사가 필요하면 백업 테이블을 조회할 수 있다.
- 운영 테이블에는 진행 중인 시즌만 남아 역할이 명확해진다.

**대체 내용:** 결과를 별도 테이블로 복사하지 않고 `ranking_entry`에 기록하면서, entry 시즌 파티션은 SETTLING에 작업 테이블로 꺼냈다가 되돌리고 SETTLED 이후에 분리한다 ([D-49](#d-49)).

### <a id="d-21"></a>D-21. result 생성은 운영 테이블 밖에서 청크로 — 대체됨 (D-49)

**결정:** entry를 EXCHANGE로 먼저 분리한 뒤, 분리된 테이블에 정렬 인덱스를 추가하고 커서 기반 청크로 result를 적재한다.

**검토한 대안:** 운영 테이블에서 단일 `INSERT ... SELECT` + 윈도우 함수.

**이유**
- 단일 대형 트랜잭션은 언두 증가, 복제 지연, 버퍼 풀 오염을 일으킨다.
- 정렬 인덱스를 운영 테이블에 두면 모든 스코어 제출의 쓰기 비용이 늘어난다.
- 청크 적재는 중단 시 `MAX(final_rank)` 기준으로 이어갈 수 있다.

**대체 내용:** 운영 테이블 밖(작업 테이블)에서 정렬 인덱스를 붙여 청크로 처리하는 방식은 유지한다. 처리 내용이 result INSERT에서 작업 테이블의 `final_rank` UPDATE로 바뀌었다 ([D-49](#d-49)).

### <a id="d-22"></a>D-22. 고정 이름 작업 테이블 `ranking_entry_settling` — 대체됨 (D-49)

**결정:** entry EXCHANGE 대상을 고정 이름 작업 테이블로 하고, result 적재 후 시즌 이름으로 RENAME한다. `GET_LOCK`으로 정산을 하나씩 처리한다.

**검토한 대안:** 처음부터 시즌별 이름 테이블로 EXCHANGE.

**이유:** 백업 테이블 이름이 시즌마다 달라지면 result 적재 SP가 동적 SQL이 된다. 고정 이름이면 무거운 적재 단계를 정적 SQL로 유지할 수 있다. 작업 테이블의 `(ranking_id, season_no)` 컬럼으로 어느 시즌인지 확인 가능해 자가 복구 판단에 지장이 없다.

**대체 내용:** 고정 이름 작업 테이블과 `GET_LOCK` 직렬화는 유지한다. 가순위를 매긴 뒤 RENAME하지 않고 entry 파티션으로 되돌린다. 작업 테이블은 재생성 없이 계속 쓴다 ([D-49](#d-49)).

### <a id="d-23"></a>D-23. 과거 시즌 조회는 Top N만 영구 보관 — 확정

**결정:** 정산 확정 시 시즌별 상위 `hall_size`를 `ranking_hall`에 적재해 영구 보관한다.

**검토한 대안**
- Redis에 시즌 키를 계속 유지
- 회원별 역대 순위 테이블
- 백업 테이블 직접 조회

**이유**
- 확정된 순위는 정렬 구조가 필요 없어 Redis에 둘 이유가 없다.
- 회원별 역대 순위는 참가자 × 시즌만큼 행이 쌓여 일간 랭킹 기준 연간 수억 행이 될 수 있다.
- 백업 테이블 조회는 테이블 이름이 동적이라 데이터 경로에 동적 SQL이 들어간다.
- Top N은 시즌당 수십~수백 행이라 영구 보관 부담이 없다.

### <a id="d-49"></a>D-49. 정산 결과를 `ranking_entry`에 함께 기록 — 확정

**결정:** `ranking_result`를 두지 않는다. 결과 컬럼(`final_rank`, `reward_code`, `reward_status`, `reward_held`, `sanctioned`, `delivered_at`)을 `ranking_entry`에 처음부터 두고, SETTLING은 시즌 파티션을 작업 테이블로 꺼내 가순위를 UPDATE한 뒤 같은 파티션으로 되돌린다. entry 시즌 파티션은 자기 시즌과 다음 시즌이 모두 SETTLED일 때 백업으로 분리한다. D-20을 대체하고 [D-21](#d-21), D-22의 일부를 바꾼다.

**배경:** 기존 설계는 시즌 종료 시 참가자 전원의 스코어를 result로 복사하고, 원본은 entry 백업으로 남겨 장기적으로 두 벌을 보관했다. 참가자가 많고 주기가 짧은 랭킹에서 저장 공간과 백업 크기가 두 배가 된다.

**검토한 대안**
- entry 백업만 SETTLED 시점에 삭제: 장기 이중 보관은 없어지지만 시즌마다 전원 복사 1회는 남는다.
- 작업 테이블에만 결과 컬럼을 ALTER로 추가: EXCHANGE는 컬럼·인덱스가 같아야 하므로 되돌리기 전에 다시 제거해야 한다. 데이터가 든 테이블의 컬럼 변경은 재구성이 될 수 있어 복사와 비용이 같다.
- 작업 테이블을 시즌 이름으로 RENAME해 결과로 사용: 보상·지난 시즌 조회가 동적 SQL이 되고([D-25](#d-25)), 전달이 끝나지 않으면 작업 테이블이 점유되어 다음 정산이 막힌다([D-47](#d-47)).

**이유**
- 복사가 한 번도 없고, 원본 스코어와 결과가 한 행에 남는다. 결과 계산은 `score`, `achieved_at`을 바꾸지 않으므로 원본 증거가 유지된다.
- 결과 컬럼을 처음부터 두면 작업 테이블은 `LIKE`로 항상 같은 구조라 정산 중 컬럼 DDL이 없다. 추가 저장 공간은 행당 몇 바이트다(NULL 컬럼은 비트, 기본값 0인 TINYINT 3개는 1바이트씩).
- 데이터 경로 SP는 여전히 고정 이름(`ranking_entry`)만 정적 SQL로 읽는다.

**감수할 것**
- 운영 테이블에 진행 중에는 쓰지 않는 컬럼과 결과 인덱스 2개가 붙는다. 제출은 결과 컬럼을 바꾸지 않으므로 인덱스 비용은 신규 멤버 INSERT 때만 든다.
- 끝난 시즌 파티션이 SETTLED 이후까지 운영 테이블에 남는다. 늦은 쓰기는 제출 SP의 시각 검사([4.1](01_DESIGN.md#s-4-1))로 막는다. 파티션을 지워 막던 이중 장치는 없어진다.
- 되돌리기 EXCHANGE는 `WITHOUT VALIDATION`을 쓰며, 다른 시즌 행이 없음을 PK 범위 조회로 먼저 확인한다.
- 결과 갱신이 `version`, `updated_at`을 건드리면 리컨실러가 변경분으로 오인하므로 바꾸지 않는다.

### <a id="d-52"></a>D-52. 마지막 시즌의 entry는 자기 시즌 SETTLED로 분리 — 확정

**결정:** `ranking_entry` 분리 조건 "다음 시즌도 SETTLED"는 다음 시즌이 생길 수 없는 마지막 시즌에는 적용하지 않는다. 마지막 시즌은 다음 시즌 행이 없고, 랭킹이 반복 없음이거나 종료되었거나 랭킹 `end_at`이 그 시즌 `end_at` 이하인 시즌이다.

**배경:** 단일 이벤트, 종료된 랭킹의 마지막 시즌은 다음 시즌이 없어 조건을 영원히 만족하지 못하고, entry 파티션이 운영 테이블에 무기한 남는다.

**검토한 대안**
- 운영 테이블에 계속 보관: 랭킹당 하나라 쌓이지는 않지만, 끝난 랭킹의 데이터가 운영 테이블과 파티션 수를 계속 차지한다.
- 다음 시즌 행이 없으면 무조건 분리: 반복 랭킹에서 스케줄러가 다음 시즌 행을 늦게 만들면 직전 시즌 조회 대상이 일찍 빠진다.

**이유:** 다음 시즌 조건은 "다음 시즌이 진행되는 동안 직전 시즌 전체 순위를 운영 테이블에서 조회"하기 위한 것이다([8.5](01_DESIGN.md#s-8-5)). 다음 시즌이 없으면 지킬 대상이 없다. 마지막 시즌의 조회는 hall(Top N)로 한다.

## 데이터베이스 운영

### <a id="d-24"></a>D-24. 운영 테이블은 랭킹 간 공유 — 확정

**결정:** `ranking_entry`를 모든 랭킹이 공유하고, MDL 대기는 운영 규칙으로 대응한다.

**검토한 대안:** 랭킹별 테이블 (`ranking_entry_{rankingId}`).

**이유**
- 랭킹별 테이블은 MDL이 격리되지만, 데이터 경로 SP가 동적 SQL을 써야 한다.
- DDL 세션의 짧은 `lock_wait_timeout`, 운영 테이블 긴 쿼리 금지, 한가한 시간대 실행으로 다른 랭킹이 멈추는 시간을 최악 수 초로 제한할 수 있다.

### <a id="d-25"></a>D-25. 모든 DB 로직은 SP, PREPARE는 SP_EXEC_DDL 하나 — 확정

**결정:** DB 로직은 SP로만 작성한다. 동적 SQL은 파티션 DDL에만 쓰며, `PREPARE`를 실행하는 SP는 `SP_EXEC_DDL` 하나로 한정한다.

**배경:** DBA 정책상 prepared statement 사용을 제한해 왔다.

**이유**
- MySQL은 DDL 식별자에 변수를 받지 않아 파티션 DDL에는 동적 SQL이 불가피하다.
- 실행 지점을 하나로 모으면 `DEALLOCATE` 누락(→ `max_prepared_stmt_count` 고갈)이 원천 차단되고, 실행 SQL 감사 로그를 한곳에서 남길 수 있다.
- 이름은 `INT UNSIGNED` 파라미터로만 조립해 인젝션 여지를 없앤다.
- 데이터 경로는 전부 정적 SQL이다.

**확인된 사실:** 동적 SQL이라고 인덱스를 못 타지는 않는다. 생성된 SQL은 일반 쿼리와 동일하게 최적화된다. 단점은 파싱 비용, 생성 시점 검증 불가, 인젝션 위험, 가독성이다.

### <a id="d-26"></a>D-26. 테이블명 `rank` → `ranking_entry` — 확정

**이유:** `RANK`는 MySQL 8.0.2부터 예약어다. 매번 백틱이 필요하고 실수 여지가 크다.

### <a id="d-51"></a>D-51. `SP_EXEC_DDL`은 SQL SECURITY INVOKER — 확정

**결정:** `SP_EXEC_DDL`만 `SQL SECURITY INVOKER`로 만든다. 다른 SP는 기본값(DEFINER)이다. 메인·로그 DB 모두 같다.

**배경:** 앱 계정은 스키마 단위 `EXECUTE`를 가지므로([D-44](#d-44)) 내부 헬퍼인 `SP_EXEC_DDL`도 직접 CALL할 수 있다. DEFINER면 migrate 계정 권한으로 임의 DDL이 실행되어, 앱 계정이 탈취되면 테이블을 지울 수 있다.

**검토한 대안**
- 앱 계정에 SP별로 `EXECUTE`를 부여하고 `SP_EXEC_DDL`만 제외: SP가 늘 때마다 권한을 관리해야 하고, 러너에 GRANT 권한이 필요하다.
- `SP_EXEC_DDL`이 허용 DDL 형식만 받도록 검사: 형식이 맞는 파괴적 DDL(데이터가 든 파티션 DROP)은 막지 못한다.

**이유:** INVOKER SP는 호출자 보안 문맥으로 실행된다. 관리 SP(DEFINER) 안에서 부르면 DEFINER 권한, 앱이 직접 부르면 앱 권한이라 감사 로그 INSERT부터 권한 오류(1142)로 실패한다. 로컬에서 두 경우 모두 확인했다.

## 외부 인터페이스와 보안

### <a id="d-27"></a>D-27. x-api-key 인증 + 권한 분리 — 확정

**결정:** 서버 간 호출 전용 API 키. write / read / reward 권한을 분리하고, 관리 API는 GM 도구 인증으로 분리한다.

**검토한 대안:** HMAC 서명, mTLS.

**이유:** 싱글테넌트라 호출자가 해당 프로젝트 게임 서버로 한정된다. TLS와 IP 허용 목록을 전제로 하면 API 키로 충분하다. 공용 인터넷을 경유하는 배치일 때만 서명이나 mTLS를 고려한다.

### <a id="d-53"></a>D-53. HTTP는 Fastify, Redis 클라이언트는 node-redis — 확정

**결정:** API 서버는 Fastify, Redis 클라이언트는 node-redis(v5)를 쓴다.

**검토한 대안:** Express, NestJS / ioredis.

**이유**
- Fastify: 요청 스키마 검증과 Swagger 문서화(개발 컨벤션 1장)가 같은 스키마에서 나온다. Express는 둘을 따로 붙여야 하고, NestJS는 이 규모에 비해 무겁다.
- node-redis: 클러스터, Lua(EVALSHA 자동 대체), 파이프라인 등 설계가 쓰는 기능을 모두 지원하고 Redis사가 공식으로 개발한다. ioredis는 기능은 같지만 유지보수가 최선 노력 단계이고 새 프로젝트에 node-redis를 권한다. 설치형 패키지로 오래 운영하므로 장기 지원을 택한다.

**감수할 것:** node-redis는 명령 단위 타임아웃 설정이 ioredis보다 불편하다. Redis 반영은 실패해도 응답이 성공([4.1](01_DESIGN.md#s-4-1))이라, 반영 호출 한 곳에서 타임아웃을 감싼다.

### <a id="d-54"></a>D-54. API 키는 SHA-256 해시 저장, 메모리 목록으로 인증 — 확정

**결정:** `api_credential`에 키의 SHA-256 해시와 권한 비트를 둔다. API는 활성 키 목록을 메모리에 두고 30초마다 다시 읽는다. 발급·폐기는 CLI로 한다.

**검토한 대안:** bcrypt 해시, 요청마다 DB 조회, 짧은 TTL 캐시.

**이유**
- 키는 32바이트 난수라 무차별 대입이 불가능하다. 느린 해시는 비밀번호처럼 엔트로피가 낮은 값을 위한 것이다.
- 키는 설치본마다 몇 개뿐이라 전체 목록을 들고 있는 편이 단순하고, 제출 경로에 DB 왕복이 늘지 않는다.

**감수할 것:** 폐기·발급이 최대 30초 늦게 반영된다. 키 변경은 드물고 교체 절차로 피할 수 있으며, 긴급 시 재시작으로 즉시 반영한다.

**부가 결정:** 제출 API는 `requestId` 멱등 키를 받는다. SUM은 재시도 시 중복 가산되므로 필수다.

### <a id="d-55"></a>D-55. 결과 코드는 SP와 API가 한 번호 공간, 대역이 발생 위치 — 확정

**결정:** SP의 RESULT 코드를 변환 없이 API 응답 `result`와 `log_ranking_submit.result_code`로 내보낸다. 대역으로 발생 위치를 나눈다: 10xx~12xx SP(도메인별), 20xx API 계층, 5000 앱 미분류, 50001 DB 시스템 오류. 성공 응답은 `{ result: 0, data }`, 실패는 `{ result, message }`다.

**검토한 대안:** API 전용 코드 체계를 두고 SP 코드를 매핑, 5자리 코드(도메인 2자리 + 상세 3자리).

**이유**
- 코드만 보고 어느 계층·도메인에서 났는지 안다. 매핑하면 API 코드만으로는 DB 거부인지 API 거부인지 구분되지 않는다.
- 새 오류는 `codes.ts`와 `ERROR_MAP`에 한 줄씩이다. 매핑은 매핑 표까지 세 곳을 고쳐야 하고, 누락 시 미분류 오류(500)로 바뀌어도 리뷰에서 잘 보이지 않는다.
- 매핑의 장점(SP 번호를 바꿔도 계약 유지)은 이미 쓴 값의 의미를 바꾸지 않는 규칙(D-46과 같은 원칙) 아래서 쓸 일이 없다.
- 5자리는 여유가 크지만, 랭킹 한 도메인 안에서 기능이 정해진 프로젝트라 도메인당 99개를 넘길 여지가 낮다.

**감수할 것:** SP 코드가 곧 외부 계약이다. 한 도메인이 99개를 넘으면 예비 대역을 주며, 그만큼 대역 규칙이 흐려진다.

**부가 결정:** Swagger UI는 `API_DOCS=1`일 때만 연다. 설치본 운영 환경에 API 구조를 기본으로 드러내지 않는다.

### <a id="d-56"></a>D-56. API는 랭킹 정의를 메모리에 두고 30초마다 다시 읽는다 — 확정

**결정:** API는 기동 시 `SP_LIST_RANKING_DEFINITION`으로 랭킹 정의(순위 규칙, `max_submit_per_min`)를 읽어 메모리에 두고 30초마다 다시 읽는다. 기동 시 읽기 실패는 기동을 거부한다.

**검토한 대안:** `SP_SUBMIT_SCORE` 결과에 정의 컬럼을 덧붙임.

**이유**
- 제출 빈도 검사는 SP보다 먼저 해야 한다([4.1](01_DESIGN.md#s-4-1)). SP 결과로 받으면 빈도 검사를 SP 뒤로 옮겨야 하고, 그러면 거부할 요청도 DB 쓰기를 거친다.
- 순위 조회 API도 정렬 방향과 composite 디코드에 같은 값이 필요하다.
- 순위 규칙은 등록 후 불변이라 캐시가 늦어도 틀리지 않는다. 제출 허용 여부(`status`)는 SP가 원장 기준으로 판정한다.

**감수할 것:** `max_submit_per_min` 변경과 새 랭킹은 최대 30초 늦게 반영된다. 새 랭킹은 그동안 1101을 받는다.

**부가 결정:** 캐시에 없는 랭킹은 API가 SP를 부르지 않고 1101로 거부한다. SP의 1101과 같은 의미라 같은 코드를 쓴다. 같은 상황에 코드가 둘이면 게임 서버의 처리만 늘어나기 때문이다. [D-55](#d-55) "대역 = 발생 위치"의 예외다.

### <a id="d-57"></a>D-57. 최종 순위의 동점 키는 Redis와 같은 시간 슬롯이다 — 확정

**결정:** 정산 가순위 정렬은 `achieved_at`(ms) 대신 composite와 같은 시간 슬롯 `FLOOR((achieved_at − 시즌 시작) / time_unit)`으로 동점을 가르고, 같은 슬롯이면 `member_id`로 가른다. 정렬 인덱스는 이 식의 함수 키로 만든다. → 구현 방식은 [D-65](#d-65)(가상 컬럼).

**검토한 대안:** 최종 순위는 ms 기준으로 두고 Redis 순위를 근사로 안내.

**이유**
- 게임 서버가 보여 준 실시간 순위와 보상 순위가 다르면 문의와 분쟁이 생긴다.
- time_unit은 운영자가 "이 단위 안은 동시"로 정한 값이라, 최종 순위도 같은 정의를 따르는 것이 일관된다.

**감수할 것:** 정렬 인덱스 식이 시즌마다 다르고(시즌 시작 상수), 가순위 UPDATE가 같은 식을 정확히 써야 인덱스를 탄다. MS 랭킹은 결과가 이전과 같다.

### <a id="d-58"></a>D-58. 순위 조회: 현재 시즌은 end_at까지 캐시(30초 상한, D-81), 조회 불가는 2007 — 확정

**결정:** API는 랭킹별 현재 시즌을 `SP_GET_CURRENT_SEASON`으로 읽어 `end_at`까지 메모리에 둔다(조기 종료 반영을 위해 최대 30초, [D-81](#d-81)). 순위는 Redis에서만 읽고, 센티넬이 없거나 Redis를 쓸 수 없으면 2007(503)으로 응답한다. 순위표에 없는 멤버는 `rank: null`(200)이다. 응답에 달성 시각은 넣지 않는다.

**검토한 대안**
- 현재 시즌을 요청마다 SP로 조회: 조회 트래픽이 그대로 DB 부하가 된다.
- 30초 정의 재조회에 현재·다음 시즌 포함: 다음 시즌 행이 미리 없으면 경계에서 최대 30초 비어 보인다.
- 조회 불가를 200 + `ready: false`로: 게임 서버가 플래그를 따로 확인해야 하고 Redis 장애도 성공처럼 보인다.

**이유**
- 시즌은 `end_at` 전에는 바뀌지 않으므로 시즌당 랭킹마다 DB 조회 1회로 경계 시각까지 정확하다.
- 현재 시즌의 순위 출처는 Redis뿐이다([8.5](01_DESIGN.md#s-8-5)). 일부만 찬 순위표를 내보내면 틀린 순위가 표시된다.
- 기록이 없는 멤버는 정상 상태다. 상위 조회에 `memberId`를 함께 보냈을 때 목록까지 실패하지 않는다.
- composite의 시간 부분은 time_unit으로 내림된 값이라 실제 달성 시각으로 오해될 수 있다.

**감수할 것:** 현재 시즌이 없는 랭킹(종료, 시즌 사이 공백)은 캐시하지 않아 조회마다 SP를 부른다. 앱 시계가 DB보다 빠르면 경계 직후 잠시 매 요청 SP를 다시 읽는다.

### <a id="d-28"></a>D-28. Anti-cheat는 이상 징후 탐지 + 검수 연동 — 확정

**결정:** 하드 검증(거부), 소프트 탐지(표시), 어뷰징 포인트(근거 합산)로 구성한다. 자동 조치는 보상 보류까지만 한다.
> D-77로 바뀜: 보상 보류를 두지 않는다. 포인트는 검수 목록의 정렬 기준이다.

**이유**
- 랭킹 서버는 스코어를 의미 없는 정수로 다루므로 플레이 정당성은 판단할 수 없다. 그것은 게임 서버의 책임이다.
- 통계적 이상은 오탐이 있으므로 거부하면 정상 유저가 피해를 본다.
- 포인트를 근거에서 계산해야 "왜 이 점수인가"에 답할 수 있다.
- 포인트는 검수 대상을 좁히는 지표이며 판정이 아니다.

**부가 결정:** 시즌 간 포인트는 합산하지 않고 참고로만 표시한다. 한 번의 오탐이 계속 불이익이 되지 않게 한다.

### <a id="d-50"></a>D-50. 랭킹 정의 테이블 이름을 `ranking_definition`으로 변경 — 확정

**결정:** `ranking_def`를 `ranking_definition`으로 바꾼다. 다른 테이블명은 유지한다. 이 결정 이전 기록의 `ranking_def`는 당시 이름 그대로 둔다.

**배경:** 테이블명을 개발자가 처음 봐도 뜻을 알 수 있게 다듬자는 검토에서 `ranking_def`, `ranking_entry`, `ranking_hall` 세 개가 후보였다.

**검토한 대안**

**이유:** 축약 없이 읽히는 이름이 개발자에게 바로 뜻이 전해진다. DB 적용 전이라 바꾸는 비용이 문서와 DDL 수정뿐이다.

### <a id="d-59"></a>D-59. 시즌 Top N 테이블 이름을 `ranking_season_top`으로 변경 — 확정

**결정:** `ranking_hall`을 `ranking_season_top`으로, `ranking_definition.hall_size`를 `top_size`로 바꾼다. 조회 API는 `/v1/rankings/{id}/seasons/{n}/top`으로 한다. 이 결정 이전 기록의 `ranking_hall`·`hall_size`는 당시 이름 그대로 둔다.

**배경:** D-50에서 `ranking_top` 안을 기각하고 `ranking_hall`을 유지했으나, hall(명예의 전당)이 처음 보는 개발자에게 뜻이 바로 전해지지 않았다.

**검토한 대안**
- `ranking_hall` 유지: 변경은 없으나 이름만으로 내용을 알기 어렵다.
- `ranking_hall_of_fame`: 뜻은 명확하나 길다.
- `ranking_top_rankers`: 다른 테이블이 모두 단수형이고 ranking이 반복된다.

**이유:** `ranking_` 뒤에 무엇의 기록인지를 붙이는 다른 테이블명과 같은 구조이고, 시즌 단위라는 것이 이름에 드러난다. 이 테이블을 쓰는 SP·코드가 아직 없어 바꾸는 비용이 마이그레이션 2개(이름만 변경, V015·V016)와 문서 수정뿐이다. 적용된 V001·V009는 러너가 변경을 거부하므로 고치지 않는다.

### <a id="d-30"></a>D-30. 제출 시 시즌 번호 필수 — 확정

**결정:** 스코어 제출은 `seasonNo`를 필수로 받는다. 게임 서버는 플레이 시작 시점의 시즌 번호를 보내고, 현재 OPEN 시즌과 다르면 `SEASON_MISMATCH`로 거부한다.

**배경:** 시즌을 넘는 멱등 재시도를 검토하다 발견했다. `wait_period = 0`이면 시즌 N 종료 직후 N+1이 열리므로, 시각 검사만으로는 시즌 N에서 시작한 플레이가 N+1에 반영된다. D-14의 엄격 마감이 다음 시즌이 열려 있는 경우에는 지켜지지 않는 빈틈이었다.

**검토한 대안**
- 시즌 번호 없이, 멱등 키를 현재 시즌에서 못 찾으면 직전 시즌 로그도 조회
- 시즌 번호를 선택값으로 받기

**이유**
- 게임 서버는 클라이언트에 시즌 정보(번호, 종료까지 남은 시간)를 보여줘야 하므로 어차피 시즌을 알고 있다.
- 플레이가 어느 시즌에 속하는지 명시되어 엄격 마감이 항상 지켜진다.
- 재전송은 같은 시즌 번호를 들고 오므로 멱등 조회가 해당 시즌 파티션 하나로 끝난다. 직전 시즌 조회 같은 우회가 필요 없다.
- 과거 시즌 번호는 시각 검사에서 거부되어 조작이 불가능하다.

### <a id="d-31"></a>D-31. SUM 결과가 score_max를 넘으면 거부 — 확정

**검토한 대안:** `score_max`로 맞추기(클램프).

**이유:** `score_max`는 비트 예산의 경계다. 넘는다는 것은 정의가 잘못되었거나 비정상 제출이라는 신호이므로 조용히 맞추지 않고 거부한다. 거부 사유는 멱등 키(`rejected`)와 제출 이력에 남아 어뷰징 탐지 근거가 된다.

### <a id="d-32"></a>D-32. SUM 첫 제출의 증분이 0 이하면 entry 행을 만들지 않음 — 확정

**이유:** 0점 행이 생기면 참가자 수와 Redis 순위표에 0점 유저가 들어가고, PERCENT 보상 구간의 분모가 틀어진다. 제출 자체는 로그에 남긴다.

**보완:** 처음에는 "음수면"이었으나, 증분 0도 같은 결과(0점 행)를 만들므로 "0 이하"로 넓혔다.

**응답:** 오류가 아니라 정상 처리다. `RESULT 0`과 `score = 0`, `version = 0`, `achieved_at = NULL`을 반환한다. 멱등 키는 기록한다. 재전송은 다른 경우와 같이 현재 entry 상태를 반환하며, 그때도 행이 없으면 같은 값을 반환한다. 앱은 `version = 0`이면 Redis 반영을 건너뛴다. 별도 실패 코드로 돌려주면 게임 서버가 실패로 보고 재시도한다.

### <a id="d-33"></a>D-33. 멱등 키 충돌은 거부 — 확정

**결정:** 같은 `requestId`에 다른 내용(member, 값)이 오면 `IDEMPOTENCY_CONFLICT`로 거부한다.

**이유:** 이전 결과를 그대로 반환하면 게임 서버의 키 생성 버그가 조용히 묻힌다.

### <a id="d-34"></a>D-34. 비 ACTIVE 랭킹은 제출 거부 — 확정

**이유:** 쓰기 차단은 시각으로 한다([D-11](#d-11))는 원칙과 별개로, 관리자가 랭킹을 일시 중지(PAUSED)하거나 종료(ENDED)하면 즉시 반영되어야 한다.

### <a id="d-35"></a>D-35. 개발 컨벤션과 설계의 충돌 처리 — 확정

**결정**

| 항목 | 따르는 쪽 |
| --- | --- |
| 컬럼·키 구조 (복합 PK, DATETIME(3)) | 설계 |
| 상태·구분값 컬럼 타입 | 컨벤션 — `TINYINT UNSIGNED` + COMMENT 매핑 ([D-46](#d-46)) |
| 표기 규칙 (COMMENT, 헤더 주석, charset/collation, 인덱스 이름) | 컨벤션 |
| SP 이름 (대문자) | 컨벤션 |
| SP 결과 반환 | 컨벤션 RESULT 규약 (단, [D-36](#d-36)) |
| 로그 테이블 위치 | `log_ddl_audit`는 메인 DB, 제출 이력은 로그 DB ([D-48](#d-48)) |
| 식별자 컬럼 콜레이션 | `utf8mb4_bin` (`member_id`, `request_id`, `ranking_code`, `reward_code`, `rule_code`) |
| 락 헬퍼의 DB 접근 | SP 미사용, `GET_LOCK` 직접 호출 (컨벤션 예외) |

**이유**
- 파티션 테이블은 파티션 키가 PK에 포함되어야 하므로 대리키 기반 컨벤션을 그대로 적용할 수 없다.
- 설계 문서의 소문자 SP 이름은 설명용이었다. 이름 규칙은 기존 컨벤션이 기준이다.
- `log_ddl_audit`는 `SP_EXEC_DDL` 안에서 기록해야 하므로 물리 분리할 수 없다. 제출 로그는 멱등 키와 이력으로 나눠 이력만 분리한다 ([D-48](#d-48)).
- 식별자는 대소문자를 구분하지 않으면 `UserA`와 `usera`가 같은 member로 합쳐진다.
- 러너는 SP가 생성되기 전에도 락을 잡아야 하므로 락 헬퍼는 SP를 거칠 수 없다.

### <a id="d-36"></a>D-36. SP 오류 처리: 내부 헬퍼는 RESIGNAL — 확정

**결정:** `SP_EXEC_DDL`은 실패 시 감사 로그를 기록하고 `RESIGNAL`한다. 앱이 호출하는 SP는 RESULT 규약을 따르며, 관리 SP는 헬퍼의 예외를 받아 `50001`로 반환한다.

**검토한 대안:** 헬퍼까지 RESULT 규약 적용.

**이유:** 헬퍼가 RESULT를 SELECT하면 호출한 SP에서 결과셋이 이중으로 나간다. 내부 헬퍼는 예외로 실패를 알리고, 앱과의 경계에서만 규약으로 변환한다.

### <a id="d-37"></a>D-37. 마이그레이션: 테이블은 버전, SP는 반복 — 대체됨 (실행 방식은 D-39)

**결정:** 테이블은 버전 마이그레이션, SP는 체크섬이 바뀌면 DROP 후 CREATE하는 반복 마이그레이션으로 관리한다. 통합 SQL 파일은 두지 않는다.

**이유:** 버전 체계와 통합 파일을 함께 두면 같은 내용을 두 곳에서 관리하게 된다. 설치형 배포는 기동 시 자동 적용이 필요하므로 러너가 기준이다.

**대체 내용:** 파일 관리 방식(테이블은 버전, SP는 반복, 통합 파일 없음)은 유지한다. "기동 시 자동 적용"은 [D-38](#d-38), D-39로 대체되었다.

## 배포와 운영

### <a id="d-38"></a>D-38. DB 변경이 있는 배포는 중단 패치 — 확정

**결정:** 앱 코드만 바뀌는 배포는 롤링으로, DB(테이블, SP) 변경이 있는 배포는 전체 중지 → migrate → 기동으로 한다. 게임 점검 시간에 맞추는 것을 원칙으로 한다.

**배경:** 기동 시 자동 마이그레이션([D-37](#d-37))을 스케일아웃 환경의 롤링 배포에서 검토했다. 문제는 다음과 같았다.
- MySQL 8.4에는 `CREATE OR REPLACE PROCEDURE`가 없어 SP를 바꾸는 DROP과 CREATE 사이에 호출이 실패한다.
- 구버전 인스턴스가 바뀐 스키마·SP를 그대로 사용한다.
- 반복 마이그레이션이 구버전 인스턴스 재시작으로 SP를 구버전 본문으로 되돌린다.
- 공유 운영 테이블의 DDL이 MDL 대기에 걸리면 모든 랭킹의 쓰기가 멈춘다.

**검토한 대안:** 무중단 마이그레이션 (배포 전 migrate 1회, expand/contract, 시그니처 변경 SP는 `_V2` 새 이름, 본문 수정은 1305 에러 재시도로 공백 흡수, 운영 테이블은 INSTANT DDL만)

**이유**
- 위 대안으로도 공유 테이블 DDL의 짧은 정지, INSTANT가 아닌 변경, backfill, 롤백 제약(contract 이후 불가), Redis·API 호환은 남는다. 무중단은 러너 하나로 보장되지 않고 변경 규칙과 배포 절차 전체가 필요하다.
- 게임은 정기 점검이 있는 도메인이다. 게임이 내려가 있으면 스코어 제출이 없으므로 랭킹 서버 중지의 영향이 없다.
- 중단 패치에서는 구버전·신버전이 공존하지 않으므로 expand/contract, SP 버전 이름, 재시도 같은 장치가 모두 필요 없어진다.
- 시즌 마감은 시각, 정산·아카이브는 상태 관측 기반이라 중단 후 기동하면 밀린 단계부터 이어간다.

**남긴 원칙:** 운영 테이블 대량 backfill 금지, INSTANT가 아닌 변경은 소요 시간을 측정해 점검 시간 안에 끝나는지 확인.

### <a id="d-39"></a>D-39. 기동 시에는 마이그레이션을 확인만 — 확정

**결정:** 적용은 `npm run migrate`로만 한다. API와 워커는 기동 시 스키마(SQL 파일 목록·체크섬)가 패키지와 다르면 기동을 거부한다. `migrate`는 살아 있는 인스턴스 하트비트가 있거나, 역행 검사(미지의 테이블 버전 파일, 낮은 package version)에 걸리면 실행을 거부한다.

**이유**

| 실수 | 차단 |
| --- | --- |
| 인스턴스를 내리지 않고 migrate | 하트비트 검사 |
| migrate 없이 새 버전 기동 | 기동 시 스키마 확인 |
| DB 변경 패키지를 실수로 롤링 배포 | 기동 시 스키마 확인으로 데이터 안전은 항상 보장. 구버전 유지(가용성)는 실패한 배포를 멈추는 도구일 때만 성립하며 pm2는 해당하지 않음 (아래 보완) |
| migrate 하트비트 검사 직후 구버전 기동 | 기동·migrate가 같은 락 사용, 기동은 하트비트를 락보다 먼저 기록 |
| 구버전 패키지로 migrate (테이블 변경 포함) | 미지의 테이블 버전 검사 |
| 구버전 패키지로 migrate (SP만 변경) | package version 역행 검사 |

- 자동 적용으로 두면 DB 변경 패키지를 롤링 배포했을 때 첫 인스턴스가 마이그레이션을 실행해 D-38의 문제가 그대로 발생한다.
- 하트비트 검사에는 강제 실행 옵션을 두지 않는다. "급하니 일단 실행"이 되면 장치의 의미가 사라진다. 비정상 종료한 인스턴스의 하트비트는 30초 후 만료된다.
- 하트비트로 판단하므로 프로세스 관리 방식(pm2, systemd, Docker)과 무관하게 동작한다.

**보완 (1단계 구현 체크 후)**
- **롤링 시 보장 범위 (pm2 실험 후 정정):** 처음에는 "헬스체크를 기다리는 롤링이면 배포가 멈추고 구버전이 계속 서비스한다"고 보았으나, 보장을 둘로 나눠야 했다.
  - 데이터 안전(틀린 스키마로 서비스하지 않음)은 기동 시 스키마 확인으로 도구와 무관하게 성립한다.
  - 가용성(구버전 유지)은 실패한 배포를 멈추는 도구일 때만 성립한다. pm2는 `--wait-ready`를 써도 `listen_timeout` 후 구버전을 내려 약 32초 뒤 전체 중단되었고, fork 모드 reload는 즉시 재시작했다.
  - 결론: DB 변경 패키지에는 pm2 reload를 금지하고 `upgrade`만 사용한다. Kubernetes RollingUpdate처럼 진행을 멈추는 도구는 가용성까지 기대할 수 있으나 검증 전이다.
- **migrate 직후 구버전 기동 빈틈:** migrate가 하트비트 검사를 통과한 직후 구버전 패키지가 기동하면, 구 스키마와 일치해 확인을 통과하고 하트비트도 아직 없어 검사에 보이지 않았다. 감수하지 않고 막았다. 기동은 하트비트 기록 → 락 → 스키마 확인 순서로, migrate는 락 → 하트비트 검사 → 적용 순서로 실행한다. 어느 쪽이 락을 먼저 잡아도 한쪽이 거부된다. 비용은 기동 시 짧은 락 하나뿐이다.
- **버전의 정의:** 기동 시 확인은 버전 번호가 아니라 SQL 파일 목록·체크섬 비교다. migrate 역행 검사는 DB에 기록된 `package.json` version과 비교한다. 사람이 version을 올리는 규칙에만 의존하지 않도록, DB에 적용 기록이 있는데 패키지에 없는 테이블 버전 파일이 있으면 자동으로 거부한다. SP만 바뀐 경우는 파일로 신구를 구분할 수 없어 version 규칙에 의존한다.
- **하트비트 정리:** `instance_id`는 PID 대신 기동마다 생성하는 UUID다(PID 재사용으로 다른 인스턴스 행을 덮어쓰는 것 방지). 비정상 종료로 남은 행은 하트비트 루프가 1시간 넘은 것을 삭제한다.

### <a id="d-40"></a>D-40. upgrade 스크립트는 환경 명령 주입 방식 — 확정

**결정:** `npm run upgrade`가 중지 → 하트비트 소멸 대기 → migrate → 기동 → 새 버전 하트비트 확인을 수행한다. 중지·기동 명령은 `UPGRADE_STOP_CMD`, `UPGRADE_START_CMD` 환경 변수로 받는다.

**배경:** 프로세스 중지·기동 방식이 배포 환경마다 달라 Docker 작업 때로 미루려 했다.

**이유**
- 환경에 따라 달라지는 것은 명령뿐이므로, 명령을 주입받으면 스크립트 자체는 지금 확정할 수 있다. Docker 도입 시 값만 바꾼다.
- 마지막 단계에서 기대 구성(API 수, 워커 수)만큼 새 버전 하트비트를 확인해 "올렸는데 실제로는 안 떴다"는 상황을 잡는다.

### <a id="d-41"></a>D-41. GET_LOCK은 전용 커넥션, 청크마다 보유 확인 — 확정

**결정:** 락 헬퍼는 풀에서 전용 커넥션을 받아 작업이 끝날 때까지 반납하지 않는다. 장시간 잡은 청크마다 `IS_USED_LOCK(name) = CONNECTION_ID()`로 락 보유를 확인하고, 아니면 중단한다.

**배경:** 워커 스케일아웃 시 정산 등 잡의 단일 실행을 검토했다.

**이유**
- `GET_LOCK`은 커넥션에 묶인다. 풀에 반납하면 다른 코드가 그 커넥션을 쓰면서 락이 엉뚱하게 유지되거나 풀린다.
- 커넥션 단절이나 MySQL 페일오버 시 락이 풀려, 첫 워커가 작업 중인데 다른 워커가 같은 잡을 시작할 수 있다. 단계가 멱등이고 PK가 중복을 막아 데이터가 깨지지는 않지만, 겹치는 상황 자체를 줄인다.

**확인된 사실:** 워커 스케일아웃은 잡 처리량이 아니라 가용성을 위한 것이다. 잡은 항상 한 곳에서만 돈다.

### <a id="d-42"></a>D-42. Redis 반영은 센티넬이 있을 때만 — 확정

**결정:** 모든 Redis 반영 Lua는 시즌 센티넬(`:ready`)이 있을 때만 쓴다. 센티넬은 시즌 OPEN 시 설정하고, 정산의 키 삭제는 센티넬부터 지운다. (설정 주체는 D-60에서 복구 잡으로 변경)

**배경:** API 스케일아웃 시, MySQL 커밋 후 Redis 반영 재시도가 정산의 시즌 키 삭제보다 늦게 도착하는 경우를 검토했다.

**이유**
- 늦은 반영이 지운 시즌 키를 멤버 몇 명으로 되살리고, 그 키는 아무도 지우지 않아 메모리에 영원히 남는다. 인스턴스가 많을수록 확률이 커진다.
- 정산 결과는 MySQL 기준으로 만들어지므로 늦은 반영을 버려도 손실이 없다.
- 재구축용으로 이미 있던 센티넬을 쓰기 허용 조건으로 확장한 것이라 새 장치가 필요 없다. BEST도 조건 확인을 위해 Lua로 반영한다.

### <a id="d-43"></a>D-43. 멱등 재전송은 현재 entry 상태를 반환 — 확정

**결정:** 같은 `requestId`, 같은 내용의 재전송은 반영하지 않고 처리 당시 결과가 아닌 현재 entry 상태를 `replayed = 1`과 함께 반환한다.

**이유**
- 앱은 응답으로 Redis를 반영한다. 처리 당시 값을 돌려주면 그 사이 다른 제출로 version이 올라간 경우 오래된 값을 반영하려다 거부되거나, 반영 경로가 낡은 값을 기준으로 움직인다. 최신 행이어야 version 비교가 맞게 동작한다.
- 멱등 키에는 처리 당시의 달성 시각과 version을 보관하지 않으므로, 당시 결과를 완전히 재현하려면 로그 컬럼을 늘려야 한다.
- 게임 서버 입장에서도 재시도의 목적은 "반영되었는가, 지금 점수는 얼마인가"이므로 현재 상태가 더 유용하다.

### <a id="d-44"></a>D-44. DB 계정 분리: migrate 계정과 앱 계정 — 확정

**결정:** `podium_migrate`는 `podium_de` 전체 권한과 `PROCESS`를 가지며 SP의 DEFINER가 된다. `podium_app`은 `EXECUTE`만 가진다. API·워커는 앱 계정으로, `migrate`·`upgrade`는 migrate 계정으로 접속한다.

**이유**
- 모든 DB 로직이 SP이므로([D-25](#d-25)) 앱 계정은 실행 권한만 있으면 된다. 앱 계정이 탈취돼도 테이블을 직접 읽거나 고칠 수 없다.
- SP는 `SQL SECURITY DEFINER`라 DEFINER 권한으로 실행된다. 정산 전 `INNODB_TRX` 조회([7.1](01_DESIGN.md#s-7-1))에 필요한 `PROCESS`도 DEFINER인 migrate 계정이 가진다.
- API·워커만 도는 호스트에는 migrate 계정 정보를 두지 않는다.

**예외:** 락 헬퍼의 `GET_LOCK`([D-41](#d-41))은 권한이 필요 없어 앱 계정으로 직접 호출한다.

**절차:** [03_DEV_SETUP 3.1](03_DEV_SETUP.md#31-스키마와-계정-생성)

### <a id="d-45"></a>D-45. 시즌 주기는 초 단위 고정 길이까지 허용, 하한 없음 — 확정

**결정:** `cycle_type`의 `DAYS`를 `FIXED`(`cycle_value`초)로 바꾼다. 최소 주기는 두지 않고, `정산 시작 지연 + review_period`가 시즌 길이 안에 들어가지 않으면 등록을 거부한다. 정산 시작 지연은 `max(settle_delay, 리컨실러 안전마진 + 리컨실러 실행 주기)`다. `wait_period`는 제한하지 않는다.

**검토한 대안:** `HOURS` 추가, 환경 변수 하한(`MIN_CYCLE_SEC`), 코드 고정 하한, `wait_period < 시즌 길이` 조건.

**이유**
- 운영상 쓸 일은 드물지만, 하루 안에 여러 번 도는 이벤트 같은 최악의 경우를 스키마 변경 없이 받기 위해서다. 단위를 초 하나로 통일하면 DAYS·HOURS·MINUTES를 따로 둘 필요가 없다.
- 짧은 주기의 실제 위험은 정산 적체다. 이를 시간 조건으로 등록 시점에 막는다.
- 정산은 `settle_at`뿐 아니라 리컨실러 동기화 시각 조건([7.1](01_DESIGN.md#s-7-1))도 만족해야 시작하므로, `settle_delay`만으로 계산하면 짧은 주기에서 실제 시작이 더 늦어 적체를 막지 못한다.
- `wait_period`는 시즌 사이의 공백이라 정산과 겹치지 않는다. 제한하면 "7일 시즌을 한 달에 한 번" 같은 설정이 막힌다.

**감수할 것:** 주기가 매우 짧으면 공유 운영 테이블에 파티션 DDL이 자주 걸린다([11.1](01_DESIGN.md#s-11-1)). 하한은 운영 판단에 맡긴다.

### <a id="d-46"></a>D-46. 상태·구분값은 ENUM 대신 TINYINT 코드 + const — 확정

**결정:** 상태·구분값 컬럼은 `TINYINT UNSIGNED`로 저장한다. 값의 의미는 `src/core/codes.ts`의 const에서만 관리하고, 컬럼 COMMENT에 코드→의미 매핑과 const 이름(`[codes.SeasonStatus]` 등)을 적는다. SP는 같은 숫자를 리터럴로 쓴다. D-35의 "ENUM은 설계를 따름"을 대체한다.

**대상:** `ranking_def`(status, update_rule, sort_order, time_unit, cycle_type), `ranking_reward_tier.range_type`, `ranking_season.status`, `ranking_entry.reward_status`([D-49](#d-49) 이전 `ranking_result`). 이미 숫자였던 `log_ddl_audit.status`, `instance_heartbeat.process_type`과 관리 SP의 파티션 대상 코드도 같은 파일에서 관리한다.

**이유**
- 개발 컨벤션 16.1(상태값은 TINYINT + COMMENT 매핑)과 맞춘다.
- ENUM은 값 추가·순서 변경이 테이블 정의 변경이라 운영 테이블에 DDL이 필요하다. 코드는 const와 COMMENT만 고치면 된다.
- 앱과 SP가 같은 숫자를 쓰고 의미를 한 곳에서 관리한다.

**규칙**
- 이미 저장된 값의 의미는 바꾸지 않는다. 새 의미는 새 번호로 추가한다.
- "없음"을 뜻하는 값은 0(`CycleType.NONE`, `RewardStatus.NONE`), 그 외는 1부터 쓴다.
- `SeasonStatus`는 진행 순서대로 번호를 매겨 크기 비교로 단계를 판단할 수 있게 한다.

### <a id="d-47"></a>D-47. 전달 미완료 시즌은 기한 없이 보관, GM 강제 종료만 허용 — 확정

**결정:** DELIVERING 시즌은 PENDING이 모두 ack될 때까지 운영 테이블에 둔다. 결과를 담은 테이블([D-49](#d-49) 이후 `ranking_entry`)은 자기 시즌과 다음 시즌이 모두 SETTLED일 때만 백업으로 분리한다. ack 정체와 DELIVERING 적체는 알림으로 알리고, 포기는 GM 강제 종료(`forced_by`, `forced_reason` 기록)로만 한다.

**배경:** 게임 서버 연동이 한 시즌 넘게 장애이면, 기존 "다음 시즌 SETTLED 시 분리" 조건으로는 다음 시즌이 먼저 끝났을 때 전달 중인 시즌의 result가 백업으로 빠져 남은 PENDING을 조회할 수 없었다.

**검토한 대안**
- 보상 API가 백업 테이블도 조회: 테이블 이름이 시즌마다 달라 동적 SQL이 필요하다 ([D-23](#d-23), [D-25](#d-25) 위배).
- 일정 기간 후 자동 포기: 랭킹 서버가 보상을 버리는 경로가 생긴다. 자동으로 해결되지 않으면 멈추고 알린다는 원칙([01_DESIGN 1.5](01_DESIGN.md#s-1-5))에 어긋난다.

**감수할 것:** 장애 동안 해당 시즌 파티션이 운영 테이블에 남는다. 짧은 주기 랭킹은 파티션 상한(8192)에 다가갈 수 있어 적체 알림으로 대응한다.

### <a id="d-48"></a>D-48. 제출 로그를 멱등 키(메인 DB)와 이력(로그 DB)으로 분리 — 확정

**결정:** 제출 로그를 나눈다. 멱등 판별에 필요한 최소 컬럼은 메인 DB `ranking_submit_key`에 두어 반영과 같은 트랜잭션에서 기록한다. 전체 이력은 로그 DB `podium_de_log.log_ranking_submit`에 커밋 후 별도로 기록한다. 첫 라이브 전에 적용한다.

**배경:** 제출 로그는 제출마다 쌓이는 가장 큰 테이블이다. 메인 DB에 두면 로그 문제가 서비스 장애로 번진다.

**이유 (라이브 운영 관점)**
- 장애 격리: 로그 정리 실패나 디스크 포화가 제출·정산·보상을 멈추지 않는다.
- 복구 시간: 메인 DB 크기가 로그에 끌려가지 않아 백업·복구가 빠르다.
- 사람의 임의 조회: 조사용 조회가 공유 운영 테이블에 MDL과 부하를 주지 않는다.
- 로그 스키마 변경이 메인 운영 테이블 DDL이 되지 않는다.
- 분리는 운영 데이터가 없을 때 가장 싸다. 라이브 후에는 설치본마다 진행 중 시즌의 멱등 키 전환이 필요하다.

**검토한 대안:** 메인 DB 유지 후 부하 테스트로 판단. 성능 기준으로는 타당하지만 장애 격리와 전환 비용을 고려하지 않았다.

**부가 결정**
- 제출 이력은 인증과 요청 형식 검사를 통과한 모든 제출을 결과와 무관하게 `result_code`로 남긴다(빈도 초과, 비활성, 시즌 불일치, 충돌, 재전송 포함). 인증 실패와 형식 오류는 컬럼을 채울 수 없거나 아직 제출로 볼 수 없어 앱 로그로만 남긴다.
- 로그 DB 보관은 날짜 기준 일 파티션이며, 데이터가 찬 파티션을 DROP한다(서비스 경로가 아님 — D-72에서 월 테이블 이동으로 바꿈). 파티션 DDL을 위해 로그 DB에도 `SP_EXEC_DDL`과 그 감사 로그 `log_ddl_audit`를 하나씩 둔다 — "PREPARE는 `SP_EXEC_DDL`에만"은 DB마다 하나로 적용한다. 로그 DB 파티션 이름은 `DATE` 파라미터로만 조립한다.
- 기동 시 로그 DB가 접속 불가면 경고 후 기동하고, 접속되는데 스키마가 다르면 기동을 거부한다.
- 로그 DB 접속 정보와 계정은 메인과 별도로 필수로 받는다(`DB_LOG_HOST`, `DB_LOG_PORT`, `DB_LOG_NAME`, `DB_LOG_APP_*`, `DB_LOG_MIGRATE_*`). 비었을 때 메인 값으로 대체하면 설정 누락이 조용히 로그를 메인 인스턴스에 쌓아 장애 격리를 무너뜨린다. 누락은 기동을 막고, 접속 장애는 경고만 한다.

**감수할 것:** DB, 커넥션 풀, 쓰기 경로가 하나씩 늘어난다. 로그 DB 장애 시 이력이 빠질 수 있다. 정산·검수에 필요한 `rejected`는 메인에 남겨 이력 유실이 정산에 영향을 주지 않게 한다.

## 3단계 구현 착수 시 결정

### <a id="d-60"></a>D-60. 센티넬은 복구 잡이 만든다, 대상 시즌은 시각으로 고른다 — 확정

**결정**
- 센티넬은 워커의 복구 잡(L2·L3)만 만든다. 스케줄러는 센티넬을 다루지 않는다. 새로 열린 시즌은 "센티넬 없음"으로 감지되어 재구축되며, 빈 시즌의 재구축은 센티넬 설정만 한다.
- 복구 대상은 `start_at ≤ NOW + 60초`이고 상태가 CLOSED 이하인 시즌이다. 시작 전 시즌의 센티넬을 미리 세운다.
- 재구축의 교체는 Lua 하나로 순위표·version HASH `RENAME`과 센티넬 설정을 함께 한다. 임시 ZSET이 적재 수보다 작으면 교체하지 않는다. 센티넬 값은 따라잡은 DB 시각 T이며 L2도 끝날 때 갱신한다.
- 복구 잡과 정산의 시즌 키 삭제는 같은 락(`podium:recovery`)을 잡는다.
  같은 락 안에서 상태 SETTLING 커밋 → 키 삭제 순서로 한다.
- composite 계산과 랭킹 정의 캐시는 `src/core`에 두고 API와 워커가 함께 쓴다.

**배경:** 3단계(자가 복구) 구현에서 센티넬의 설정 주체, 대상 시즌 선정, 교체 절차를 검토했다.

**이유**
- 센티넬을 만드는 경로가 하나면 "처음 만들 때"와 "유실 후 다시 만들 때"가 같은 코드다. 스케줄러가 늦거나 멈춰도 시즌이 열린다.
- 60초 미리 세우면 시즌 경계마다 조회가 2007이 되지 않는다. 연달아 시작하는 시즌에서 앞 시즌 재구축이 길어도 다음 시즌이 막히지 않는다. 게임 서버는 2007을 장애 때만 받는다. 전제는 시즌 행과 파티션이 시작 60초 전에 있는 것이다(4단계 스케줄러가 미리 유지).
- 제출은 시즌을 시각으로 받는다([D-11](#d-11)). 복구 대상도 시각으로 골라야 둘이 같은 시즌을 가리킨다. CLOSED까지 포함해야 마감 직전 커밋까지 따라잡고 동기화 시각이 `end_at`을 넘어 정산 시작 조건([7.1](01_DESIGN.md#s-7-1))을 채운다.
- 교체와 센티넬 설정 사이의 틈에서 버려지는 반영과, 두 명령 사이에 죽었을 때 남는 반쯤 바뀐 상태가 없어진다.
- 같은 락이 아니면 재구축이 정산의 키 삭제 뒤에 센티넬을 되살릴 수 있다.
- composite 계산이 API와 워커에서 어긋나면 리컨실러가 매 주기 같은 행을 "다르다"고 보고 다시 쓴다.

### <a id="d-61"></a>D-61. 규모 목표는 설치본당 MAU 100만, 대형 게임은 별도 구축 — 확정

**결정:** 설치본 하나당 MAU 100만(DAU 20만, 제출 피크 약 460건/초, 시즌 참가자 최대 100만)을 목표로 한다. 이를 넘는 대형 게임은 이 구조를 키우지 않고 별도로 구축한다 ([01_DESIGN 1.7](01_DESIGN.md#s-1-7)).

**배경:** 3단계 재구축을 검토하다 MAU 1억에서의 동작을 확인했다. Redis 메모리, 재구축 시간, MySQL 쓰기 한계, 정산 시간이 모두 구조 변경을 요구했다.

**이유**
- MAU 1억은 세계 최상위 몇 개 타이틀만 도달하는 규모다. 대부분의 설치 대상은 MAU 100만 이하다.
- 1억을 기본 전제로 두면 MySQL 분할, Redis 클러스터 같은 구조가 소·중 규모 설치본에 비용과 운영 부담으로 그대로 얹힌다.
- 대형 게임은 어차피 전용 인프라와 팀을 갖추므로, 같은 패키지를 늘리는 것보다 별도로 구축하는 편이 맞다.
- 목표 피크의 약 5배(2,300건/초)를 이미 측정해 두어서, 목표 안에서는 대수만 늘리면 된다.
- 100만 명 로컬 실측: 재구축 BEST 약 6초, SUM 약 11초, Redis 메모리 약 95·148바이트/명.

**감수할 것:** 목표를 넘는 게임에는 이 패키지를 그대로 권할 수 없다. 넘을 때 바꿔야 할 지점은 [01_DESIGN 1.7](01_DESIGN.md#s-1-7)에 남긴다.

## 4단계 구현 착수 시 결정

### <a id="d-62"></a>D-62. 시즌 경계는 앱이 계산하고, WEEKLY 요일은 start_at을 따른다 — 확정

**결정:** DAILY·WEEKLY·MONTHLY 시즌 경계는 워커가 Node 내장 Intl로 timezone 벽시계 기준으로 계산하고 UTC로 SP에 넘긴다. SP는 번호 연속과 시각 순서만 검증한다. WEEKLY는 랭킹 `start_at`의 요일부터 7일씩 끊는다.

**검토한 대안:** SP에서 `CONVERT_TZ`로 계산, WEEKLY 월요일(ISO) 고정.

**이유**
- `CONVERT_TZ`는 mysql 시간대 테이블이 있어야 동작한다. 설치마다 적재 절차가 늘고, Windows MySQL은 기본으로 비어 있다.
- Intl은 의존성 추가 없이 IANA 시간대와 DST를 다룬다. 벽시계로 더하므로 DST 전환일도 자정에서 끊긴다.
- 게임마다 주간 리셋 요일이 다르다. `start_at` 요일을 쓰면 컬럼을 추가하지 않고 설정 하나로 맞춘다.

**감수할 것:** 경계 계산이 DB 밖에 있어, SP만 보고는 시즌 기간이 맞는지 알 수 없다. 계산은 회귀 테스트(C1~C7)로 고정한다.

### <a id="d-63"></a>D-63. 반복 랭킹은 "현재 + 다음 2개"를 개수로 유지하고, 지난 시즌은 파티션 없이 번호를 이어 만든다 — 확정

**결정:** 스케줄러는 반복 랭킹마다 끝나지 않은 시즌을 3개로 유지한다(단일 시즌·영구 랭킹은 1개). 만들 시점에 이미 끝난 시즌(워커 장기 정지, 과거 `start_at`)도 번호를 이어 만들되, 행만 만들고 파티션은 만들지 않는다. 이어 만들 시즌 수에는 제한을 두지 않는다.

**검토한 대안:** 시간 창(예: 24시간) 앞까지 유지, 지나간 주기를 건너뛰고 현재 시각부터 시작, 지나간 시즌에도 파티션 생성(처음 구현), 이어 만들 시즌이 일정 수(예: 100)를 넘으면 거부.

**이유**
- 시간 창은 짧은 FIXED 주기에서 시즌·파티션이 수백 개가 되어 파티션 상한(8192)과 DDL 빈도에 걸린다. 개수는 주기와 무관하게 상한이 정해진다.
- 3개면 워커가 시즌 2개 길이만큼 멈춰도 시작 60초 전 시즌 행·파티션([D-60](#d-60))이 유지된다.
- 시즌 번호가 달력 주기와 어긋나면 게임 서버가 계산하거나 캐시한 번호와 달라진다. 지나간 시즌은 빈 채로 바로 CLOSED가 되어 정산 비용이 거의 없다.
- 지나간 시즌은 제출이 시각 검사로 막혀 파티션이 영원히 빈다. 빈 파티션은 모든 랭킹이 공유하는 테이블의 파티션 상한과 DDL만 늘린다. 정산·아카이브는 파티션 없는 시즌을 빈 시즌으로 처리한다.
- 개수 제한을 두지 않는 것은 그런 상황이 등록 실수(과거 `start_at`, 너무 짧은 FIXED 주기)이기 때문이다. 실수의 책임은 등록한 사람에게 두고, 시스템은 공유 테이블이 망가지지 않는 것(파티션 미생성)만 보장한다. 명백한 실수는 6단계 등록 검증에서 거른다.

**감수할 것:** 긴 정지나 등록 실수 뒤에는 지나간 시즌 수만큼 시즌 행과 빈 정산이 생긴다. 극단적인 실수(1년 전 시작의 짧은 FIXED)는 시즌 행이 수십만 개가 될 수 있다.

### <a id="d-64"></a>D-64. GM 조작, 보상 보류 판정, 정산 완료 웹훅은 6단계로 미룬다 — 확정

**결정:** 4단계는 시즌 생성부터 보상 전달 API까지 자동 경로만 구현한다. 다음 항목은 6단계(운영 도구·Anti-cheat)에서 구현한다. 검수 보류·조기 확정, held → PENDING/REJECTED 전환, DELIVERING 강제 종료, `reward_held` 임계치 판정, 정산 완료 웹훅.
> D-77로 바뀜: held 전환과 `reward_held` 판정은 하지 않는다.
> 정산 완료 웹훅은 6단계에서 빼고 2차 이후 범위로 옮긴다(이름은 "보상 준비 완료 웹훅"). 주기 확인만으로 보상을 모두 가져갈 수 있다.

**이유**
- GM 조작은 관리 인증([10.1](01_DESIGN.md#s-10-1))이 필요해 운영 도구와 함께 만드는 편이 맞다.
- `reward_held`의 근거인 `ranking_suspicion`은 6단계 전까지 비어 있고, `suspicion_config` 형식도 정해지지 않았다.
- 게임 서버는 `GET /v1/rewards/pending` 주기 확인만으로 보상을 모두 가져갈 수 있다([7.7](01_DESIGN.md#s-7-7)). 웹훅은 신호일 뿐이다.

**감수할 것:** 6단계 전에는 검수 기간 동안 사람이 개입할 수 없어, 기간이 지나면 그대로 확정된다. 보상 보류도 없다.

### <a id="d-65"></a>D-65. 정산 정렬 키는 함수 키 대신 가상 컬럼 settle_slot + 인덱스 — 확정

**결정:** D-57의 시간 슬롯 정렬 인덱스를 함수 키로 만들지 않는다. 꺼낼 때 같은 식의 가상 생성 컬럼 `settle_slot`과 그 인덱스를 한 ALTER로 추가하고, 되돌리기 전에 둘 다 제거한다. 가순위 UPDATE는 컬럼 이름으로 정렬한다.

**배경:** 4단계 가순위 SP 작성 중 EXPLAIN으로 확인했다. 함수 키 인덱스는 상수를 글자 그대로 넣은 식에서만 쓰이고, 변수로 쓴 식(정적 SP가 쓸 수 있는 형태)은 PRIMARY + filesort가 된다. 가상 컬럼 + 인덱스는 `Using index`.

**검토한 대안:** 함수 키 유지 + 동적 SQL(PREPARE) — `SP_EXEC_DDL`만 PREPARE한다는 [D-25](#d-25) 위배. 인덱스 없이 한 번의 대형 UPDATE — 언두·복제 지연([7.3](01_DESIGN.md#s-7-3)).

**이유**
- 함수 키도 내부적으로는 숨은 가상 컬럼이라 비용이 같고, 이름을 붙이면 정적 SQL로 참조할 수 있다.
- 청크마다 남은 행 전체를 정렬하면 100만 명에서 정렬이 200번 반복된다.

**감수할 것:** 작업 테이블 구조 변경이 인덱스 하나에서 컬럼 + 인덱스로 늘었다. 되돌리기 전 제거가 빠지면 EXCHANGE가 1736으로 실패한다. SP가 상태를 관측해 걷어내고 회귀 테스트 T9로 확인한다.

### <a id="d-66"></a>D-66. 시각은 세션 UTC로 통일하고, 시스템 뷰의 시각만 CONVERT_TZ로 바꾼다 — 확정

**결정:** 저장·비교하는 시각은 모두 세션 `time_zone='+00:00'` 기준 UTC다. 서버 시스템 시간대로 나오는 `INNODB_TRX.trx_started`만 `CONVERT_TZ(x, 'SYSTEM', '+00:00')`로 바꿔 비교한다.
SP와 앱의 직접 쿼리는 `NOW(3)` 대신 `UTC_TIMESTAMP(3)`을 쓴다. 풀을 거치지 않는 세션(서버 기본 시간대)에서 `NOW(3)`이 KST로 나오는 것을 실측했다(UTC 10:27 / NOW 19:27). 앱 로그도 프로세스 `TZ=UTC`로 같은 시간대에 둔다(회귀 테스트 G9: 세션 +09:00에서도 UTC 기록).

**배경:** 정산 시작 조건([7.1](01_DESIGN.md#s-7-1))의 미종료 트랜잭션 검사가 열린 트랜잭션을 잡지 못했다(회귀 테스트 T1). `trx_started`가 세션 시간대를 무시하고 시스템 시간대(KST)로 나와 UTC `end_at`보다 9시간 늦게 보였다.

**검토한 대안:** 모든 시각 비교에 CONVERT_TZ 적용 — 이미 UTC인 값이 이중 변환되고, 이름 시간대는 시간대 테이블 없이 NULL이다. DB 서버 시간대를 UTC로 강제 — 설치 환경 요구가 늘고, 잘못 설정해도 조용히 틀린다.

**이유**
- `'SYSTEM'`은 시간대 테이블 없이 동작하고, 서버 시간대가 무엇이든 맞는다.
- 예외를 시스템 뷰 하나로 좁혀 두면 나머지 코드는 시간대를 신경 쓰지 않는다.

**감수할 것:** 시스템 시간대에 DST가 있으면 되돌아가는 1시간 동안 변환이 어긋날 수 있다. DB 서버는 UTC나 DST 없는 시간대로 둔다.

### <a id="d-67"></a>D-67. MONTHLY 시즌 시작일은 1~28일만 허용한다 — 확정

**결정:** MONTHLY 랭킹에서 timezone 기준 시작일이 28일을 넘는 시즌이 다음 시즌으로 이어지면 거부한다. 첫 시즌뿐 아니라 `wait_period`로 밀린 이후 시즌도 같다. 그 시즌이 마지막 시즌이면(랭킹 `end_at`에서 잘려 다음 시즌이 없으면) 허용한다.

**배경:** 4단계 시즌 계산은 다음 달에 같은 날이 없으면 말일로 붙였다. 붙인 날부터 다음 달을 세므로 31일 시작은 2월 이후 매달 28일로 밀린다.

**검토한 대안:** 매달 말일(월말 시즌)로 해석, 처음 시작일을 기억해 달마다 다시 맞춤.

**이유**
- 29일은 있는 달과 없는 달이 있어 매달 같은 날로 시작할 수 없다. 시작일로 쓸 수 있는 날은 모든 달에 있는 1~28일뿐이다.
- 조용히 밀리는 일정은 게임 공지와 어긋나도 알아채기 어렵다. 거부하고 알리는 편이 안전하다([1.5](01_DESIGN.md#s-1-5)).
- 월말 시즌이 필요하면 1일 시작으로 같은 결과를 얻는다(전월 말일 24시 = 1일 0시).

**감수할 것:** 29\~31일 시작은 쓸 수 없다. 관리 API는 등록·수정 시점에 거부한다(2010). DB에 직접 넣은 정의는 스케줄러가 시즌을 만들 때 막혀, 시즌 없이 남고 오류 로그로만 드러난다.

### <a id="d-68"></a>D-68. 확정은 커서를 메모리에만 두고 매번 처음부터 멱등하게 돈다 — 확정

**결정:** FINALIZING의 순위 재부여 커서는 저장하지 않는다. 중단되면 다음 실행이 제재 제외부터 다시 한 바퀴 돈다. 제재 행은 구간과 무관하게 모두 REJECTED이다. 구간 판정 규칙은 [D-69](#d-69).

**배경:** 새 순위는 가순위보다 크지 않아, 처리한 행(1..커서)과 남은 행(커서보다 큰 가순위)이 섞여도 final_rank 순서가 원래 순서와 같다. 그래서 0부터 다시 돌아도 같은 결과가 나온다.

**검토한 대안:** 커서를 `ranking_season` 컬럼에 저장 — 컬럼·V 파일이 늘고, 중단은 드물다. 가순위 기준으로 구간 안이던 제재자만 REJECTED — 제외 전 참가자 수로 PERCENT를 따로 계산해야 한다.

**이유**
- 중단 비용이 시즌 한 바퀴뿐이다(청크 UPDATE, 같은 값은 쓰기 없음).

**감수할 것:** REJECTED 건수에 원래 보상 구간 밖이던 제재자도 들어간다. 확정 도중 제재가 추가되면(6단계 운영 도구) 다시 돌 때 반영되지만, 이미 DELIVERING으로 넘어간 뒤에는 "지급 후 제재"([7.8](01_DESIGN.md#s-7-8))로 처리한다. → D-78로 바뀜: 확정은 `review_until` 전 제재만 제외하므로, 확정 도중 추가된 제재는 다시 돌아도 반영되지 않고 검수 후 제재로 표시만 한다.

### <a id="d-69"></a>D-69. PERCENT는 "내 앞 사람 비율"로 판정하고, 겹치면 RANK가 먼저다 — 확정

**결정:**
- PERCENT 구간은 순위 r의 앞 사람 비율 `(r−1)/P`가 `[from−1, to)`%면 해당한다. 상위 t% 누적 인원은 `ceil(P×t/100)`이다.
- 구간이 겹치면 RANK가 PERCENT보다 먼저이고, 같은 종류끼리는 `tier_no`가 작은 쪽이다.
- 보상 순위 사이 공백은 확정 때 경고 로그로 알린다.

**배경:**
- 처음 구현은 백분위 올림 `CEIL(r×100/P) ∈ [from, to]`였다. 1위의 백분위가 `100/P`%라 P < 100이면 상위 1% 구간이 0명이고, P = 1이면 혼자 참가한 1위가 51\~100% 보상을 받았다. P ≥ 100에서도 누적 인원이 `floor(P×t/100)`이라, P 100\~100,000 가운데 98.9%에서 1명씩 달랐다.
- RANK + PERCENT 혼합 구성을 P 1\~1,000(500,500건) 전수 검사했다. `tier_no` 순서만 보면, PERCENT를 작은 번호로 넣었을 때 상위 10위가 RANK 대신 PERCENT 보상을 받았다(9,955건). PERCENT를 11%부터 두면 11위\~상위 10% 경계가 보상 없이 비었다(40,950건). 둘 다 경고 없이 지나갔다.

**검토한 대안:**
- 백분위 올림 유지: t%를 넘겨 주지 않지만, 참가자가 적으면 상위 구간이 빈다.
- 인원 반올림: P < 50이면 상위 1%가 다시 0명이 된다.
- 구간별 최소·최대 인원 컬럼: 유연하지만 테이블 변경이 필요하다.
- 공백을 오류로 막기: 의도된 공백(예: 하위권 보상 없음)과 구분할 수 없다.

**이유**
- 1위는 앞 사람이 없으므로 참가자 수와 무관하게 최상위 구간이다. "앞에 t% 미만이 있으면 상위 t%"로 플레이어에게 설명할 수 있다.
- t%보다 적게 주는 경우가 없어, 경계에 걸친 사람이 빠지는 불만이 없다.
- 정수 비교만 써 나눗셈 오차가 없다. P 1~100은 SQL 식과 JS 계산 5,050건이 일치하고 빈틈·겹침·역전이 없었다.
- RANK를 먼저 판정하면 "상위권은 정확한 인원, 그 아래는 비율"이라는 흔한 구성이 `tier_no` 순서와 무관하게 의도대로 나뉜다.
- 한 행에 보상 하나라 중복 보상은 구조적으로 생기지 않는다.

**감수할 것:**
- 경계마다 t%보다 최대 1명 더 준다(P=199의 상위 1%는 2명 = 1.005%).
- RANK와 PERCENT가 겹치는 순위에 일부러 PERCENT 보상을 주는 구성은 쓸 수 없다.
- 공백은 경고뿐이라 로그를 보지 않으면 놓친다. 공백은 참가자 수 P에 따라 달라 등록 시점에 확정할 수 없다. 화면 표시는 7단계 웹 프론트엔드에서 검토한다.

### <a id="d-70"></a>D-70. SETTLED 전이와 전달 감시는 워커 전달 잡이 한다 — 확정

**결정:**
- DELIVERING → SETTLED는 ack API가 아니라 워커 전달 잡이 한다. 잡은 `DELIVERY_INTERVAL_MS`(기본 30초)마다 DELIVERING 시즌의 남은 전달 대상(PENDING, 보류 제외)을 세고, 0인 시즌을 `SP_UPDATE_SEASON_SETTLED`로 넘긴다.
- 전이는 조건부 UPDATE 한 문장(`status = 7 AND NOT EXISTS 남은 대상`)이다. 남아 있으면 1016으로 거부하고 다음 주기에 다시 본다.
- 전달 잡은 정산 잡과 다른 락(`podium:delivery`)으로 돈다. ack 정체(`DELIVERY_STALL_SEC`)와 적체(`DELIVERY_BACKLOG_MAX`)도 이 잡이 판정한다.
- 결과·보상 API는 DELIVERING 전 시즌을 1003으로 거부한다.

**배경:**
- 보상 대상이 0건인 시즌(빈 시즌, 보상 구간 없음, 전원 제재)은 게임 서버가 ack할 것이 없다. ack에서 전이하면 이런 시즌은 영원히 DELIVERING에 남는다.
- ack 정체·적체 경고는 ack가 오지 않을 때 필요한 것이라, ack 경로에서는 판정할 수 없다.
- FINALIZING 중에는 `SP_UPDATE_FINAL_RANK`가 `final_rank`, `reward_status`를 다시 쓴다. 이때 ack가 DELIVERED로 바꾸면 다음 청크가 PENDING으로 덮을 수 있다.

**검토한 대안:**
- ack SP가 마지막 PENDING을 처리하면 같은 트랜잭션에서 SETTLED로 전이: 지연이 없다. 하지만 0건 시즌을 끝낼 다른 경로가 어차피 필요하다. ack마다 시즌 행을 잠가 동시 ack가 한 줄로 서고, 잠금 순서(season 3 → entry 7)도 ack SP에 들어온다.
- `SP_UPDATE_SEASON_DELIVERING`에서 대상 0건이면 바로 SETTLED: 0건 시즌은 해결된다. 하지만 상태 흐름에 건너뛰기가 생기고, 보류 건이 PENDING으로 전환(6단계)되는 경우를 다시 따로 처리해야 한다.
- 정산 잡(5초 주기)에 붙이기: 큰 시즌 확정이 몇 분 걸리는 동안 SETTLED와 경고가 밀린다. 남은 수를 5초마다 세는 비용도 든다.

**이유**
- 0건 시즌, 마지막 ack, 6단계의 보류 전환·강제 종료 뒤가 모두 같은 한 경로로 끝난다.
- ack SP는 `ranking_entry`만 잠근다. 동시 ack 5개, ack 도중 데드락(1213 → 50001 후 재시도)을 실제로 일으켜도 결과가 같았다(회귀 R9·R11).
- 전이 조건을 문장 안에서 다시 보므로, 목록을 읽은 뒤 무엇이 바뀌어도 남은 대상이 있는 시즌은 넘어가지 않는다.

**감수할 것:**
- 마지막 ack 뒤 SETTLED까지 최대 `DELIVERY_INTERVAL_MS`만큼 늦다. SETTLED 뒤의 백업 분리(1시간 주기)도 그만큼 늦게 시작한다.
- 주기마다 DELIVERING 시즌마다 남은 수를 센다(`ix_reward_status` 범위 + `reward_held` 행 조회). 게임 서버 장애로 큰 시즌이 많이 쌓이면 그만큼 읽는다. 적체 경고로 드러난다.
- ack 정체 기준 시각은 워커 메모리에 둔다. 워커가 재시작하면 처음부터 다시 잰다(재시작 직후 최대 `DELIVERY_STALL_SEC`만큼 경고가 늦다).
- 보류(held) 행은 남은 대상으로 세지 않는다. 보류가 남은 채 SETTLED가 되고 PENDING인 채 백업으로 분리된다([7.7](01_DESIGN.md#s-7-7)). 6단계 GM 전환 전까지 보류는 항상 0이다([D-64](#d-64)). → D-77로 보류를 두지 않아 항상 0이다.

### <a id="d-71"></a>D-71. 바디는 타입을 변환하지 않고, DB 장애는 기다리지 않고 실패시킨다 — 확정

**결정:**
- 요청 바디는 타입 변환 없이 검증한다. `"10"`은 정수가 아니고, 문자열 하나를 배열로 받지 않는다. 쿼리·경로는 숫자 문자열을 변환한다.
- DB 연결 실패와 호출 실패도 SP 내부 오류와 같은 50001이다. 연결 상태는 바뀔 때만 `… db unreachable` / `… db recovered` 한 줄씩 남긴다.
- 풀 대기열은 커넥션 수 × 20까지다. API의 DB 호출은 `DB_QUERY_TIMEOUT_MS`(기본 20초)를 넘으면 커넥션을 버린다. `API_TIMEOUT_MS` 기본값은 30초에서 5초로 줄인다.

**배경:**
- Fastify 기본 검증은 바디 타입을 바꿔 받는다. 게임 서버의 직렬화 실수(숫자를 문자열로)가 조용히 통과한다.
- DB가 응답하지 않으면 처리 제한 뒤에도 풀 대기열의 요청은 지워지지 않는다. 1,500건/초면 30초에 4만 5천 건이 쌓이고, 회복 뒤 이미 포기한 요청부터 처리하느라 새 요청까지 2005를 받는다.

**검토한 대안:**
- 처리 제한만 줄이기: 응답은 빨라지지만 대기열과 묶인 커넥션은 그대로다.
- 워커에도 호출 제한 시간: 정산 청크처럼 정상적으로 긴 SP가 끊긴다.

**감수할 것:**
- 대기열 상한을 넘는 순간 정상 DB에서도 50001이 난다. 부하 테스트에서 행 락 대기가 0이었으므로 평소에는 대기열이 거의 비어 있다.
- 락 대기(5초)와 처리 제한(5초)이 같아, 락 대기를 다 채운 제출은 2005와 50001 중 하나가 된다. 둘 다 같은 `requestId` 재시도로 맞는다.
- 회귀 X1·X11(타입), X16·X17(다운), X21(데드락), X22(무응답 260건)로 확인했다.

### <a id="d-72"></a>D-72. 보관 기간이 지난 제출 이력은 월 테이블로 옮기고 개월 수로 지운다 — 확정

**결정:** 일 파티션을 EXCHANGE 두 번으로 `log_ranking_submit_YYYYMM`의 같은 날 파티션으로 옮기고, `LOG_ARCHIVE_MONTHS`(기본 12)가 지난 월 테이블을 DROP한다. 중단되면 교환 테이블 상태를 보고 이어서 한다. 스키마가 달라 실패하면 자동으로 처리하지 않고 멈춘 뒤 운영자가 정리한다.

**배경:** 일 파티션 DROP은 운영 테이블에 배타 MDL을 건 채 큰 파일을 지운다. 감사·어뷰징 조사에 90일보다 긴 보관이 필요하다.

**검토한 대안:**
- 월 파티션 하나로 합치기: 한 달 치를 복사한다.
- 스키마 불일치 시 월 테이블 자동 이름 바꾸기: 드문 일에 비해 규칙(이름, 삭제 대상)이 늘어난다.

**감수할 것:**
- 스키마 변경 배포 뒤 그 달 이동이 멈출 수 있다(정체 경고로 알림, 데이터 유실 없음).
- 월 단위라 최대 한 달 더 남는다.
- 회귀 L3~L3c, L4b, X19로 확인했다.

### <a id="d-73"></a>D-73. 시즌 백업 이름은 ID 기반으로 두고, 랭킹 코드는 COMMENT와 경고에 남긴다 — 확정

**결정:** 백업 이름은 `{원본}_r{rankingId}_s{seasonNo}`로 유지한다. 운영자가 알아볼 수 있도록 테이블 COMMENT에 랭킹 코드와 시즌 기간을 남기고, 오래된 백업 경고에도 코드와 종료일을 찍는다.

**배경:** 백업을 덤프·삭제하는 운영자가 ID만으로는 어떤 랭킹인지 알기 어렵다.

**검토한 대안:** `ranking_entry_{code}_r{id}_s{n}`. 코드는 대소문자를 구분하는데(`utf8mb4_bin`) 테이블 이름은 설치에 따라 구분하지 않아 백업끼리 겹칠 수 있다. 운영자 입력 문자열이 DDL 이름에 들어가 허용 문자 제한이 필요하고, 길이 한도(64자) 때문에 코드 길이도 줄여야 한다.

**감수할 것:**
- 표 목록만으로는 코드가 보이지 않는다(COMMENT나 경고 로그로 확인).
- COMMENT의 코드는 영숫자·`_.-` 밖의 문자가 `?`로 바뀐다.
- 회귀 B1~B7로 확인했다.

### <a id="d-74"></a>D-74. 운영 도구는 관리 HTTP API와 GM 계정·DB 세션 쿠키 인증으로 만든다 — 확정

**결정:** 6단계 운영 도구는 S2S API와 다른 프로세스·포트의 관리 HTTP API(`start:admin`)로 만든다. 웹 프론트엔드는 7단계 구현 예정이며 이 API 위에 올린다.
- **계정:** admin이 만든다. 본인 가입 신청은 없다. 첫 admin 계정은 CLI로 만든다. admin이 정한 초기 비밀번호는 첫 로그인 때 바꿔야 한다.
  > [01_DESIGN 10.4](01_DESIGN.md#s-10-4)로 구체화: 초기 비밀번호는 admin이 정하지 않고 서버가 난수로 만들어 한 번만 보여 준다.
- **역할:** viewer(조회), operator(GM 조작), admin(operator 권한과 계정 관리) 셋이다. 역할 값이 불분명하면 viewer로 취급한다.
- **세션:** 로그인하면 32바이트 난수 토큰을 httpOnly·Secure·SameSite=Strict 쿠키로 준다. DB `admin_session`에는 SHA-256 해시만 저장한다. 요청마다 DB로 검증한다. JWT와 refresh 토큰은 쓰지 않는다.
- **세션 종료:** 비밀번호를 바꾸거나 초기화하면 그 계정의 세션을 모두 끝낸다. 계정을 사용중지할 때도 같다.
- **CSRF:** SameSite와 Origin 검사로 막는다.
- **로그인 실패 제한:** 실패 횟수를 계정 행에 둔다. 연속 5회 실패하면 15분 잠근다.
- **비밀번호 해시:** `crypto.scrypt`를 쓴다.
- **검증과 상태 전이:** SP가 맡는다. SP는 요청자 GM ID를 받아 역할을 다시 확인한다.
- **감사 기록:** GM 조작은 로그 DB에 남긴다. 변경 전·후 JSON, 요청자 스냅샷을 담고 비밀 필드는 가린다. 추가만 하고 고치지 않는다.

**배경:** 웹 프론트엔드 계획이 있어 CLI는 중간 단계로만 쓰인다. 사내 쿠폰 플랫폼의 관리 콘솔 인증(JWT와 refresh, 가입 승인, DB 세션, 감사 로그)을 참고했다.

**검토한 대안:**
- CLI 먼저, API는 나중: 프론트엔드 전에 API를 새로 만들어야 한다.
- JWT(access와 refresh):
  - 이점은 DB 조회 없이 검증하는 것이다. 관리 트래픽은 많아야 초당 몇 건이라 요청마다 DB로 검증해도 된다.
  - 단점은 발급한 토큰을 만료 전에 무효화할 수 없다는 것이다. 막으려면 차단 목록 저장소가 따로 필요하고, 그러면 결국 요청마다 저장소를 조회한다.
  - 그래서 로그아웃, 비밀번호 변경, 사용중지, 역할 변경이 바로 반영되지 않는다.
  - 토큰을 브라우저 저장소(localStorage)에 두면 XSS 한 번에 긴 수명의 토큰이 털린다. httpOnly 쿠키에 두면 이 문제는 없지만, 무효화 문제는 그대로다.
  - JWT에 세션 ID를 넣고 DB로 확인하면 무효화는 되지만, 요청마다 DB를 보므로 JWT의 이점이 없고 서명 키 관리만 늘어난다.
- 세션을 Redis에 저장: Redis는 원장이 아니라 투영이다([D-02](#d-02)). Redis 장애일 때도 GM이 로그인해 대응할 수 있어야 한다.
- 가입 신청 → 승인: 인증 없이 열린 엔드포인트와 계정 상태(승인대기·반려)가 늘어난다.
- IP 단위 메모리 제한: 인스턴스 수만큼 한도가 늘어난다.
- 사내 SSO(OIDC): 연동할 인프라가 설치마다 달라 설치형 패키징과 맞지 않는다.

**감수할 것:**
- 초기 비밀번호는 사람이 전달해야 한다.
- 계정 단위 잠금이라, 남의 계정 ID로 일부러 틀리면 그 계정이 15분 잠긴다. admin이 잠금을 풀 수 있다.
- 역할이 셋이라 기능별 세분 권한은 없다(필요해지면 추가).

### <a id="d-75"></a>D-75. 제재 대상은 DB와 Redis 집합에 함께 두고, 반영 Lua 안에서 확인한다 — 확정

**결정:**
- **등록:** `ranking_exclusion`에 넣고 → Redis 제외 집합에 `SADD`하고 → 순위표에서 `ZREM`한다. 이 순서라야 `SADD` 전에 반영된 제출은 `ZREM`이 지우고, 그 뒤의 제출은 Lua가 막는다.
- **확인:** 반영 Lua(BEST, version)가 센티넬 확인 다음에 제외 집합(그 시즌, 전 시즌)을 `SISMEMBER`로 보고, 들어 있으면 쓰지 않는다. 제출 SP는 바꾸지 않는다.
- **원장:** 제재된 멤버의 제출도 원장에는 적는다. 순위는 확정할 때 제외된다([7.6](01_DESIGN.md#s-7-6)).
- **해제:** DB에서 지우고 → `SREM` → (OPEN 시즌이면) 원장 값으로 다시 반영한다. 검수가 끝나기 전(REVIEW까지) 시즌의 제재와 전 시즌(`season_no = 0`) 제재만 풀 수 있다. 검수가 끝난 시즌에 이미 붙은 `sanctioned` 표시는 그대로 둔다.
- **동기화:** 리컨실러가 1분마다 대상 시즌의 제외 목록을 DB에서 읽어 집합을 맞추고(`SADD`/`SREM`), 남은 제재 멤버를 `ZREM`한다.
- **재구축:** 센티넬을 세우기 전에 제외 집합을 DB에서 다시 채운다.

**배경:** 제출은 가장 뜨거운 경로다. 시즌 중 제재된 멤버가 다시 제출하면 API가 Redis에 다시 올린다([7.8](01_DESIGN.md#s-7-8)).

**검토한 대안:**
- 제출 SP가 `ranking_exclusion`을 PK로 확인: DB가 기준이라 어긋나지 않는다. 하지만 모든 제출에 점 조회가 하나 늘고 잠금 순서표에도 들어간다.
- Redis 장애 시 DB로 확인: Redis 장애면 반영 자체가 실패하므로 막을 것이 없다.
- API 메모리 캐시(30초 재조회): 최대 30초 동안 다시 올라가고, 리컨실러는 이미 올라간 멤버를 빼지 않는다.

**감수할 것:**
- 등록할 때 Redis가 장애면 `SADD`·`ZREM`이 실패한다. GM에게 실패를 알리고, 최대 1분 뒤 리컨실러 동기화가 맞춘다.
- RDB 복원으로 집합이 과거로 돌아가면, 그 뒤 등록한 제재가 최대 1분 동안 빠진다.

### <a id="d-76"></a>D-76. `suspicion_config`는 규칙별 가중치·임계치 JSON이고, 근거는 시즌·멤버·규칙마다 한 번만 적재한다 — 확정

**결정:**
- **형식:** `{ rules: { 규칙코드: { weight, ...임계치 } } }`.
- **규칙:** `VELOCITY`(SUM, 시간당 획득량), `RANK_JUMP`(짧은 시간의 순위 상승), `BEST_JUMP`(BEST, 이전 최고 대비 배수), `REJECTED`(하드 검증 거부) 넷으로 시작한다.
- **꺼짐:** 설정이 NULL이면 탐지하지 않는다. `rules`에 없는 규칙은 꺼진 것이다.
- **적재:** `ranking_suspicion`에 `(ranking_id, season_no, member_id, rule_code)` UNIQUE를 새 V 파일로 추가한다. 같은 규칙은 시즌당 한 번만 적재된다.
- **형식 검증:** 관리 API의 랭킹 등록·수정에서 한다(앱 ajv, SP `JSON_SCHEMA_VALID`).

**배경:** 리컨실러는 5초마다 같은 멤버를 다시 볼 수 있다. 탐지할 때마다 적재하면 포인트가 시간에 비례해 불어나 임계치를 정할 수 없다.

**검토한 대안:**
- 탐지마다 적재: 반복 어뷰징의 정도를 보여 주지만, 스캔 주기에 따라 포인트가 달라진다.
- 시간 창(예: 1시간)마다 한 번: 정도는 보이지만 시즌 길이에 따라 상한이 달라진다.

**감수할 것:**
- 포인트는 "어떤 규칙에 걸렸는가"만 나타낸다. 몇 번 걸렸는지는 `evidence`(첫 탐지 근거)로도 알 수 없다.
- 규칙별 탐지 방식(직전 값을 어디서 비교할지)은 구현할 때 정한다.

### <a id="d-77"></a>D-77. 보상 보류(held)를 두지 않고, 어뷰징 판단은 검수 기간에 끝낸다 — 확정

**결정:**
- FINALIZING에서 `reward_held`를 붙이지 않는다.
- 검수 목록은 보상 구간 안의 유저를 어뷰징 포인트 내림차순으로 보여 준다.
- GM이 제재하면 확정 때 REJECTED가 되고, 두면 그대로 지급된다.
- 판단할 시간이 더 필요하면 `review_hold`로 검수를 연장한다.
- `reward_held` 컬럼(V004)은 남겨 두고 항상 0이다.

**배경:** 보류 대상(포인트 임계치 초과자)은 검수 기간에 GM이 이미 보는 사람들이다. 확정 뒤 보류는 같은 판단을 한 번 더 미루는 것이다. 보류가 남은 채 SETTLED가 되면 GM이 전환할 수 없고([D-70](#d-70)), 기한 없이 기다리게 하면 게임이 공지한 수령 기간 뒤에 지급될 수 있다.

**검토한 대안:** 보류 유지 + 보류 처리 기한(`hold_period`, 지나면 자동 지급): 수령 기간에 상한은 생긴다. 하지만 전환 API, 기한 처리 워커, [D-70](#d-70) 수정, 대기 목록 조정이 필요하고, 판단 시간이 검수와 겹친다.

**감수할 것:**
- GM이 검수 기간에 보지 않은 의심 유저는 그대로 지급된다. 자동 안전장치가 없다.
- 검수 연장(`review_hold`)은 그 시즌 모두의 보상을 늦춘다.
- V001·V004의 컬럼 COMMENT에 보류 문구가 남는다(적용된 V 파일이라 고치지 않는다).
- SP의 `reward_held = 0` 조건은 항상 참이다. 해당 SP를 고칠 때 함께 정리한다.

### <a id="d-78"></a>D-78. 검수가 끝난 뒤의 제재는 그 시즌의 순위·보상을 바꾸지 않고 표시만 한다 — 확정

**결정:**
- **기준:** 시즌의 확정 제외 대상은 `review_until` 전에 등록된 제재(`ranking_exclusion.created_at < review_until`)뿐이다. 그 시즌 제재와 전 시즌 제재(`season_no = 0`) 모두 같다.
- **기준 시각 맞추기:** `review_until`을 실제 검수 종료 시각으로 맞춘다.
  - 조기 확정: `review_until = 지금`.
  - 보류 해제: 이미 지났으면 `review_until = 지금`.
- **검수 뒤의 제재:** 순위와 `reward_status`를 바꾸지 않는다. PENDING도 그대로 지급된다. `sanctioned = 1`만 붙인다(`ranking_entry`, `ranking_season_top`).
- **표시 시점:**
  - DELIVERING 이후 등록: 등록 SP가 바로 표시한다. 운영 테이블에서 분리된 시즌은 Top N에만 표시한다.
  - FINALIZING 중 등록: 기록만 한다. DELIVERING 전이 SP가 같은 트랜잭션에서 그 시즌의 검수 뒤 제재를 보고 표시한다.
  - 등록 SP는 시즌 행을 먼저 공유 잠금해, 전이와 엇갈려 표시가 빠지지 않게 한다(잠금 순서 season → exclusion → entry).
  - 전 시즌 제재(`season_no = 0`)의 표시는 등록 시점에 FINALIZING·DELIVERING인 시즌에만 붙인다. 이미 SETTLED인 과거 시즌에 표시하려면 그 시즌을 지정해 등록한다.
- **회수:** 게임 서버가 `sanctioned` 표시를 보고 한다.

**배경:** 검수 기간은 보상 전에 사람이 확인하는 시간이다([D-77](#d-77)). 검수가 끝난 시즌을 다시 열면 확정 중 재실행이나 ack와 엇갈려 결과가 실행 시점에 따라 달라진다.

**검토한 대안:**
- 검수 뒤라도 PENDING이면 REJECTED로 바꾸기: 아직 안 받은 어뷰저는 막는다. 하지만 ack와 경합하고, FINALIZING 중의 제재는 거부하거나 따로 처리해야 한다.
- FINALIZING 중 제재 등록 거부: GM이 다시 시도해야 하고, 거부 뒤의 처리 규칙이 여전히 필요하다.

**감수할 것:**
- 검수 뒤에 발견한 어뷰저는 아직 가져가지 않은 보상도 받는다. 회수는 게임 서버 몫이다.
- 게임 서버는 결과 API의 `sanctioned`로만 알 수 있다(따로 알리지 않는다).

### <a id="d-79"></a>D-79. 랭킹 정의는 묶음별로 수정 범위를 두고, 시즌 단위 일정 수정은 두지 않는다 — 확정

**결정:**
- **불변:** `ranking_code`, 순위 규칙(`update_rule`, `sort_order`, `score_max`, `time_unit`). 바꾸려면 새 랭킹을 등록한다.
- **시즌 일정:** `timezone`, `start_at`, `cycle_type`, `cycle_value`, `wait_period`는 첫 시즌이 시작되기 전까지만 바꾼다. 바꾸면 미리 만든 시즌을 지우고 다시 만든다.
- **운영 값:**
  - `ranking_name`, `max_delta`, `max_submit_per_min`, `suspicion_config`, `history_retention`은 언제든 바꾸고 바로 반영된다.
  - `settle_delay`, `review_period`, `top_size`, 보상 구간은 언제든 바꾸고, 아직 그 단계에 들어가지 않은 시즌부터 반영된다.
- **랭킹 종료(`end_at`, `status`):**
  - 늘리기(`end_at`을 늦추거나 NULL)는 언제든 된다. 스케줄러가 시즌을 더 만든다.
  - 줄이기는 지금 이후 어느 시각이든 된다. 그 시각이 걸친 시즌이 그 시각에 끝나는 마지막 시즌이 되고, 그 뒤 시즌은 지운다.
  - 진행 중 시즌에 걸치면 조기 종료다. 그 시즌의 `end_at`과 `settle_at`을 다시 계산하고, 이후는 평소 정산 흐름을 탄다.
  - ENDED는 되돌릴 수 없다. 진행 중 시즌은 원래 종료까지 가고(제출은 거부), SCHEDULED 시즌은 지운다.
  - PAUSED는 ACTIVE와 언제든 오가고 바로 반영된다(제출 거부). 시즌은 계속 만들어지고 정산된다.
- **재검증:** 수정 뒤에도 등록 검증([2.7](01_DESIGN.md#s-2-7))을 통과해야 한다.
- **시즌 단위 수정:** 시즌 하나의 일정을 직접 고치는 기능은 두지 않는다([3.4](01_DESIGN.md#s-3-4) 삭제). 시즌 일정은 항상 정의로 계산한다.
- **연동 안내:** 게임 서버는 `seasons/current`를 주기적으로 다시 조회하고, 제출이 1103으로 거부되면 바로 다시 조회한다([10.2](01_DESIGN.md#s-10-2)).

**배경:** 시즌은 미리 3개씩 만들어 두고([3.3](01_DESIGN.md#s-3-3)), 게임 서버는 시즌 번호를 달력으로 계산한다. 시즌 하나의 일정만 바꾸면 이후 시즌이 달력 경계에서 밀려 번호가 어긋난다. 3.4의 "이후 시즌 재계산 여부"도 정해지지 않은 채였다.

**검토한 대안:**
- 시즌 단위 수정(SCHEDULED 자유, OPEN `end_at` 변경) 유지: 이벤트 연장·조기 종료는 랭킹 `end_at`으로 모두 된다. 반복 랭킹에서는 번호 어긋남을 막을 규칙이 따로 필요하다.
- 줄이기를 진행 중 시즌 종료 이후로 제한: 공지한 시즌 기간은 지켜진다. 하지만 이벤트 버그 같은 긴급 상황에 끝낼 수단이 없다.
- 시즌 변경을 웹훅으로 알림: 웹훅 발송·서명·재시도가 필요하다. 주기 재조회와 1103 재조회로 충분하다.

**감수할 것:**
- 반복 랭킹에서 "이번 시즌만 일찍 끝내고 랭킹은 계속"은 할 수 없다. 조기 종료하면 랭킹도 끝난다.
- 조기 종료는 게임 서버가 다시 조회해야 안다. 그 전의 제출은 1103으로 거부된다(원장은 안전).

### <a id="d-80"></a>D-80. Function을 쓰고, 설치 요구사항에 `log_bin_trust_function_creators = 1`을 둔다 — 확정

**결정:** 요청자 역할 재확인은 `FN_GET_ADMIN_ROLE` 하나로 둔다(개발 컨벤션 4.2). MySQL 서버는 `log_bin_trust_function_creators = 1`이어야 한다. 설치 안내와 03_DEV_SETUP에 적는다.

**배경:** MySQL 8은 binlog가 기본으로 켜져 있다. 이때 Function을 만들려면 SUPER급 권한이나 이 설정이 필요하다. migrate 계정은 DB 단위 전체 권한만 있어 1419로 거부된다. SP는 이 제한이 없다.

**이유:**
- 이 제한은 문장 기반 복제에서 복제 서버가 Function을 다시 실행해 결과가 달라지는 것을 막기 위한 것이다. `binlog_format = ROW`(MySQL 8 기본값)는 변경된 행을 기록하므로 Function을 다시 실행하지 않는다.
- `FN_GET_ADMIN_ROLE`은 읽기만 한다(`READS SQL DATA`).

**검토한 대안:**
- SP마다 같은 SELECT를 인라인: 설치 설정은 필요 없지만, 권한 규칙이 SP 여러 곳에 복사된다.
- migrate 계정에 `SET_USER_ID` 등 전역 권한: 마이그레이션 계정이 지나치게 강해진다.

**감수할 것:** 설치마다 DBA가 서버 전역 설정을 한 번 바꿔야 한다. 빠뜨리면 `npm run migrate`가 1419로 멈춘다(05_TROUBLESHOOTING 1.1).

### <a id="d-81"></a>D-81. 랭킹 등록은 정의만 넣고, 시간 비트는 남는 비트를 모두 쓰며, ID는 DB가 정한다 — 확정

**결정:**
- 등록은 정의와 보상 구간만 넣는다. 시즌은 스케줄러가 다음 주기(5초)에 만든다. 대신 `start_at`은 지금 + 1분 이후여야 한다.
- `time_bits = 53 − bits(score_max)`. 검증식은 그대로다(`bits(score_max) + bits(최대 시즌 길이 / time_unit) ≤ 53`).
- `ranking_id`는 AUTO_INCREMENT다.
- 정의 수정은 스케줄러 락을 잡고 한다. 앱이 시즌을 읽고 계산한 값이 SP 실행 때까지 바뀌지 않는다.
- [D-79](#d-79) 보강: 늘리기는 지금 `end_at`이 지나기 전에만 된다. 잘려 있던 마지막 시즌은 새 정의로 종료를 다시 계산한다. ENDED 뒤에는 상태·일정·`end_at`을 바꿀 수 없고, 운영 값·단계 값·보상 구간은 바꿀 수 있다.
- [D-58](#d-58) 보강: API는 현재 시즌을 `end_at`과 30초 중 이른 쪽까지 캐시한다.

**이유:**
- 파티션 DDL은 트랜잭션 밖이라 등록 트랜잭션에서 시즌 행을 만들어도 결국 워커가 파티션을 채운다. 시즌 계산과 DDL을 한 곳(스케줄러)에만 둔다.
- 시간 비트를 시즌 길이에 딱 맞추면 이벤트 `end_at` 연장이 비트 부족으로 거부될 수 있다. 남는 비트를 쓰면 같은 `score_max`에서 연장 여유가 가장 크고 composite 범위(2^53)는 그대로다.
- ID를 사람이 고르면 중복 처리와 입력 실수가 생긴다. 게임 서버는 등록 응답의 ID를 쓴다.
- 스케줄러가 오래된 정의로 계산한 시즌을, 줄이기로 지운 자리에 다시 넣는 경합을 락 하나로 막는다.
- 끝난 랭킹을 늘리면 다음 시즌이 달력 경계가 아니라 옛 종료 시각에서 시작해 게임 서버의 시즌 번호 계산과 어긋난다.
- `end_at`까지 캐시하면 조기 종료 뒤에도 `seasons/current`가 원래 종료 시각을 돌려준다. [D-79](#d-79)의 "1103이면 다시 조회"가 원래 종료 시각까지 반복된다.

**검토한 대안:**
- 등록 트랜잭션에서 시즌 1 생성: 등록 직후 시즌이 보이지만, 관리 API에 시즌 계산이 하나 더 들어가고 파티션은 어차피 워커가 채운다.
- 시간 비트 = 최대 시즌 길이 기준(기존 2.4): 비트를 아끼지만 쓸 곳이 없고 연장을 막는다.
- 운영자가 ID 지정: 환경 간 ID를 맞출 수 있지만 `ranking_code`로 충분하다.

**감수할 것:**
- 등록 뒤 시즌이 보이기까지 최대 한 스케줄러 주기가 걸린다.
- 수정은 스케줄러 한 주기(파티션 DDL 포함)가 끝날 때까지 기다릴 수 있다. 3초를 넘기면 2013으로 다시 시도한다.
