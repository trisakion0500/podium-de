## 배포와 아키텍처

### D-01. 싱글테넌트, 프로젝트별 독립 배포 — 확정

**결정:** 게임 프로젝트마다 별도 인스턴스와 DB를 배포한다. (Dedicated Edition)

**배경:** 여러 프로젝트를 받는 SaaS 형태를 검토했다.

**검토한 대안**
- 멀티테넌트 공유 테이블 (`project_id`로 구분)
- 테넌트별 스키마 + 컨트롤 플레인

**이유**
- 공유 테이블은 프로젝트마다 시즌 일정이 달라 시즌 단위 파티션이 성립하지 않고, `(project_id, season)` 파티션은 개수 상한(8192)에 닿는다.
- EXCHANGE의 MDL이 테이블 전체에 걸려 한 프로젝트의 정산이 다른 프로젝트의 쓰기를 멈춘다.
- 대형 프로젝트의 부하가 다른 프로젝트에 영향을 준다(노이지 네이버).
- 독립 배포는 위 문제가 구조적으로 사라지고, 랭킹 설계에서 테넌트 식별자가 필요 없다.

**감수할 것:** 설치본 간 버전 차이, 마이그레이션 N회 실행, 소규모 프로젝트의 인프라 비용.

### D-02. MySQL 원장, Redis 투영 — 확정

**결정:** 스코어는 MySQL에 먼저 적재하고, 확정된 값을 Redis에 반영한다.

**검토한 대안**
- Redis 단독 (AOF + 레플리카)
- Redis 우선 + write-behind로 MySQL 적재

**이유**
- 보상이 걸린 랭킹은 기록 하나의 유실이 CS 사고가 된다.
- 정산, 검수, 어뷰징 조사에는 감사 가능한 원장이 필요하다.
- Redis 값이 MySQL 행에서 결정적으로 계산되므로, 복구가 "다시 계산해서 넣기"로 단순해진다.
- 싱글테넌트라 설치본당 쓰기량이 제한적이다. DAU 100만, 1인 20회 제출 기준 평균 약 230건/초, 피크 약 2,300건/초로 MySQL이 감당 가능한 범위로 추정한다. (부하 테스트로 검증 필요)

**참고:** 보상이 없는 표시 전용 랭킹이라면 Redis 단독도 타당하다.

### D-03. 달성 시각은 MySQL이 기록 — 확정

**결정:** `achieved_at`은 MySQL 마스터의 `NOW(3)`으로 기록한다.

**변경 이력:** 처음에는 Redis Lua 안에서 `TIME`으로 기록하는 안이었다. (D-02 이전)

**이유:** MySQL이 원장이 되면서 시각도 원장에 있어야 재구축 시 같은 composite를 재현할 수 있다. 시계가 하나라 서버 간 시간 차이로 순서가 뒤집히지 않는다.

### D-04. Redis 영속화는 RDB 기본, AOF 미사용 — 확정

**이유:** MySQL이 원장이라 Redis 유실은 정합성 문제가 아니다. 영속화는 재시작 후 재구축 시간을 줄이는 용도뿐이다. 스냅샷 이후 유실분은 리컨실러가 메운다. AOF는 쓰기 IO 비용에 비해 이득이 작다. 소규모 설치본은 영속화를 끌 수 있게 설정으로 연다.

## 순위 규칙

### D-05. 동점은 composite score 인코딩으로 처리 — 확정

**결정:** `score × 2^T + 시간 성분`으로 하나의 ZSET score에 점수와 달성 시각을 함께 넣는다. 비트 배분은 랭킹 등록 시 결정한다.

**이유**
- 조회 시 별도 정렬 없이 Redis 순서가 곧 순위다.
- 동점이 시간으로 모두 갈려 순위가 고유하다.
- BEST 규칙은 `ZADD GT`만으로 "같은 점수는 먼저 달성한 쪽 유지"까지 자동으로 보장된다.

**감수할 것:** double 정밀도(2^53) 안에서 점수 범위와 시간 범위가 교환 관계다. 등록 시 검증으로 막는다.

### D-06. 갱신 규칙 BEST / SUM / LATEST — 확정 (LATEST는 보류)

**결정:** 등록 시 규칙을 선택한다. 1차는 BEST, SUM. LATEST는 코드만 정의하고 등록을 막는다.

**이유**
- 스코어를 의미 없는 정수로 다루면, 규칙과 정렬 방향의 조합으로 타임어택, 누적 포인트, 최고 기록을 모두 표현할 수 있다.
- 전투력, 레벨처럼 게임 서버가 계산한 현재 값을 겨루는 랭킹은 BEST나 SUM으로 표현할 수 없어 LATEST가 필요하다.

### D-07. 감소하는 점수는 SUM의 부호 있는 증분으로 — 확정

**결정:** 점수가 깎이는 랭킹은 SUM에 음수 증분을 허용하고 하한 0으로 처리한다. `GREATEST(score + delta, 0)`

**검토한 대안**
- LATEST(절대값)로 받기
- 양수는 `GT` 경로, 음수는 version 경로로 분기

**이유**
- LATEST는 게임 서버 쪽 요청 순서가 뒤집히면 오래된 값이 최신 값을 덮어쓴다. 계산을 MySQL 행 락 안에서 하는 증분 방식이 동시성에 안전하다.
- 경로를 분기하면 `GT` 경로가 version HASH를 갱신하지 않아 비교가 틀어진다. SUM은 항상 version 경로로 통일한다.

**부가 결정:** 값이 실제로 바뀌지 않으면(0점에서 음수 증분) version과 달성 시각을 갱신하지 않는다. 동점 순서가 이유 없이 밀리는 것을 막는다.

### D-08. LATEST는 소스 시퀀스 비교 — 보류

**결정:** 게임 서버가 현재 값과 소스 시퀀스를 함께 보내고, SP는 시퀀스가 클 때만 덮어쓴다.

**이유:** 도착 순서가 곧 결과가 되는 규칙이라, 순서 보장 장치 없이는 오래된 값이 최신 값을 덮어쓴다.

### D-09. 영구 랭킹은 큰 시간 단위 허용 — 확정

**결정:** `time_unit`에 MIN, DAY를 허용하고, 영구 랭킹은 최소 30년을 커버하도록 검증한다.

**이유:** 영구 랭킹은 시즌 길이 상한이 없어 SEC 단위로는 점수 비트가 부족해진다. 영구 랭킹에서 초 단위 동점 판정의 의미는 작다.

## 시즌과 정산

### D-10. 파티션은 LIST COLUMNS(ranking_id, season_no) — 확정

**변경 이력:** RANGE COLUMNS로 검토했다가 변경했다.

**이유**
- RANGE는 경계 사이 공백이 없어, 랭킹 1의 다음 시즌 데이터가 랭킹 2의 파티션 범위로 들어갈 수 있다. 막으려면 랭킹마다 빈 future 파티션과 REORGANIZE가 필요하다.
- LIST는 순서 제약이 없어 `ADD PARTITION`만으로 어떤 시즌이든 추가할 수 있다.
- 정의되지 않은 쌍은 INSERT 에러가 나서, 잘못된 파티션에 조용히 들어가는 것보다 안전하다.

### D-11. 쓰기 차단은 시각 검사로 — 확정

**결정:** SP가 `NOW(3)`이 `[start_at, end_at)` 안인지 직접 검사한다. 상태 전이는 기록용이다.

**이유:** 종료 순간 상태를 바꾸는 잡이 늦게 돌아도 마감이 뚫리지 않는다. 자가 복구 원칙과 일치한다.

### D-12. 시즌 기간 / 정산 유예 / 대기 기간 — 확정

**결정:** 정의에 세 기간을 둔다. 정산은 시즌 사이에 직렬로 끼우지 않고 다음 시즌과 병렬로 진행한다.

**이유:** 정산을 직렬로 두면 로테이션 랭킹에 정산 시간만큼 빈 구간이 생긴다.

**변경 이력:** 대기 기간은 처음에 단일 시즌의 보상 수령 기간 역할도 했으나, D-15 이후 순수한 시즌 간 휴식 의미만 남았다.

### D-13. 정산 유예는 시각 하한 + 실제 종료 검증 — 확정

**결정:** `end_at + settle_delay` 이후, `INNODB_TRX`에 종료 전 시작된 트랜잭션이 없고 리컨실러가 따라잡았을 때 정산을 시작한다.

**이유:** 시각 검사를 통과해 이미 처리 중인 요청의 커밋이 종료 후에 끝날 수 있다. 유예 시간은 하한이고, 실제 시작은 시스템이 닫힘을 확인한 뒤다.

### D-14. 늦은 제출은 엄격 마감 — 확정 (허용 옵션은 보류, D-30으로 보완)

**결정:** `end_at` 이후 제출은 전부 거부한다.

**검토한 대안:** 게임 서버가 전투 시작 시각을 보내고, 시즌 안에서 시작한 건은 유예 시간까지 받는 방식.

**이유:** 대부분의 게임이 엄격 마감이며 공정성 시비가 없다. 허용 방식은 게임 서버가 보낸 시작 시각을 신뢰해야 한다. 긴 전투(레이드 등)를 지원할 때 `late_submit_grace` 옵션으로 추가한다.

### D-15. 보상은 수령형이 아니라 일괄 전달 — 확정

**결정:** 정산 시 대상자 보상을 확정하고, 게임 서버가 목록을 페이지 단위로 가져가 ack하는 방식으로 전달한다. 수령 기간은 랭킹 서버에 두지 않는다.

**변경 이력**
1. 수령 기간(`claim_period`)을 두는 수령형 → 접은 유저 때문에 데이터를 정리할 수 없다는 우려
2. 직전 시즌만 수령 가능, 다음 시즌 정산 시 만료 (포인터 방식)
3. 수령 마감 = 종료(N) + 대기 기간 + 다음 시즌 기간 (시각 방식)
4. **일괄 전달로 최종 변경**

**이유**
- 수령 대기 상태 자체가 사라져 결과 데이터의 보존 기간이 짧아진다.
- 접은 유저 문제는 게임 서버 우편 만료로 넘어간다.
- 게임 서버가 자기 속도로 가져가 부하 조절이 쉽고, 지급 멱등 키로 중복 지급이 없다.

**원칙 확인:** 데이터 이동 조건에 유저 행동(수령 여부)을 넣지 않는다. 전달이 장기간 멈추면 그것은 연동 장애로 보고 알림을 보낸다.

### D-16. 지급 전 검수 단계 — 확정

**결정:** 가순위 생성 → 검수 → 확정 → 전달 순서로 정산을 나눈다. 검수 기간은 시각으로 자동 종료하고, GM은 보류와 조기 확정만 할 수 있다.

**배경:** 2등이 어뷰저로 확인되었을 때, 3등이 이미 보상을 받은 뒤라면 정상 유저의 보상을 회수하고 재지급해야 한다.

**이유**
- 지급 전에 제재를 반영하고 순위를 다시 매기면 정상 유저가 피해를 보지 않는다.
- GM 승인을 기다리는 구조는 사람 손 없이 진행되어야 한다는 원칙에 어긋난다.

**부가 결정:** 확정 이후 순위는 다시 매기지 않는다. 지급 후 적발은 순위를 유지하고 어뷰저의 보상만 게임 서버가 회수한다.

### D-17. 보상 상태와 제재 표시 분리 — 확정

**결정:** `reward_status`(NONE / PENDING / DELIVERED / REJECTED)와 `sanctioned` 플래그를 별도 컬럼으로 둔다.

**이유**
- "대상 아님"과 "제재로 거부"는 결과가 같아도 CS 대응에서 구분되어야 한다.
- 지급 후 적발은 보상 상태는 DELIVERED인데 제재 표시가 필요하다. 한 컬럼으로는 경우의 수가 꼬인다.
- 제재 유저의 표시 방식은 게임마다 다르므로 랭킹 서버는 플래그만 제공한다.

## 아카이브

### D-18. EXCHANGE 1회 + 시즌별 일반 테이블 — 확정

**결정:** 운영 테이블의 시즌 파티션을 일반 테이블과 한 번 EXCHANGE하고, 그 테이블을 그대로 백업으로 사용한다.

**변경 이력**
1. 최초 안: `rank` 파티션 → `rank_archive` 파티션으로 이동 → 히스토리 테이블로 배치 복사 → `rank_archive` 파티션 삭제
2. 파티션 ↔ 파티션 직접 EXCHANGE가 불가능함을 확인하고, 중간 일반 테이블을 경유하는 2단 EXCHANGE로 수정
3. 2단 EXCHANGE 대신 정산 끝난 파티션에서 직접 복사 후 DROP 하는 안 검토
4. **EXCHANGE 1회 + 시즌별 일반 테이블로 최종 확정**

**이유**
- EXCHANGE의 가치는 운영 테이블에서 무거운 삭제를 빼내는 것이다. 데이터가 찬 파티션을 직접 DROP하면 배타 MDL을 잡은 채 파일 삭제가 진행되어 모든 랭킹의 쓰기가 멈출 수 있다. (3번 기각 이유)
- 두 번째 EXCHANGE는 같은 인스턴스, 디스크, 버퍼 풀 안에서 일어나므로 추가로 얻는 것이 없다. 대가로 테이블 하나, 스키마 동기화, 파티션 경계값 관리가 따라온다. (2번 기각 이유)
- EXCHANGE 후 일반 테이블이 곧 보관본이므로 데이터 복사가 한 번도 없다.

**확인된 사실:** EXCHANGE 대상은 반드시 비파티션 테이블이며, 교환 후에도 일반 테이블이다. 교환되는 것은 데이터 파일이다.

### D-19. 보관본은 파티션 히스토리가 아닌 시즌별 테이블 — 확정

**검토한 대안:** 히스토리 자체를 LIST COLUMNS 파티션 테이블로 두고 두 번째 EXCHANGE로 복사 없이 보관.

**이유**
- 파티션 수가 늘면 테이블 오픈, 메타데이터 처리, DDL이 무거워지고 상한(8192)이 있다.
- 히스토리 스키마 변경이 과거 시즌 전체에 걸린다.
- 시즌별 테이블은 시즌 단위로 독립 삭제, 덤프, 이동이 가능하다.

**감수할 것:** 테이블 수 증가. `history_retention`으로 상한을 두고 캐시 관련 설정을 맞춘다. 여러 시즌 교차 조회가 어렵지만 D-23으로 해소한다.

### D-20. entry 분리 시점은 SETTLING — 대체됨 (D-49)

**결정:** 정산 시작 시 entry 파티션을 분리하고, 그 데이터로 result를 생성한다.

**변경 이력:** 처음에는 검수 재계산을 위해 SETTLED까지 entry를 운영 테이블에 유지하는 안이었다.

**이유**
- 검수 단계의 순위 재부여는 result만으로 가능하다.
- 원본 조사가 필요하면 백업 테이블을 조회할 수 있다.
- 운영 테이블에는 진행 중인 시즌만 남아 역할이 명확해진다.

**대체 내용:** 결과를 별도 테이블로 복사하지 않고 `ranking_entry`에 기록하면서, entry 시즌 파티션은 SETTLING에 작업 테이블로 꺼냈다가 되돌리고 SETTLED 이후에 분리한다 (D-49).

### D-21. result 생성은 운영 테이블 밖에서 청크로 — 대체됨 (D-49)

**결정:** entry를 EXCHANGE로 먼저 분리한 뒤, 분리된 테이블에 정렬 인덱스를 추가하고 커서 기반 청크로 result를 적재한다.

**검토한 대안:** 운영 테이블에서 단일 `INSERT ... SELECT` + 윈도우 함수.

**이유**
- 단일 대형 트랜잭션은 언두 증가, 복제 지연, 버퍼 풀 오염을 일으킨다.
- 정렬 인덱스를 운영 테이블에 두면 모든 스코어 제출의 쓰기 비용이 늘어난다.
- 청크 적재는 중단 시 `MAX(final_rank)` 기준으로 이어갈 수 있다.

**대체 내용:** 운영 테이블 밖(작업 테이블)에서 정렬 인덱스를 붙여 청크로 처리하는 방식은 유지한다. 처리 내용이 result INSERT에서 작업 테이블의 `final_rank` UPDATE로 바뀌었다 (D-49).

### D-22. 고정 이름 작업 테이블 `ranking_entry_settling` — 대체됨 (D-49)

**결정:** entry EXCHANGE 대상을 고정 이름 작업 테이블로 하고, result 적재 후 시즌 이름으로 RENAME한다. `GET_LOCK`으로 정산을 하나씩 처리한다.

**검토한 대안:** 처음부터 시즌별 이름 테이블로 EXCHANGE.

**이유:** 백업 테이블 이름이 시즌마다 달라지면 result 적재 SP가 동적 SQL이 된다. 고정 이름이면 무거운 적재 단계를 정적 SQL로 유지할 수 있다. 작업 테이블의 `(ranking_id, season_no)` 컬럼으로 어느 시즌인지 확인 가능해 자가 복구 판단에 지장이 없다.

**대체 내용:** 고정 이름 작업 테이블과 `GET_LOCK` 직렬화는 유지한다. 가순위를 매긴 뒤 RENAME하지 않고 entry 파티션으로 되돌린다. 작업 테이블은 재생성 없이 계속 쓴다 (D-49).

### D-23. 과거 시즌 조회는 Top N만 영구 보관 — 확정

**결정:** 정산 확정 시 시즌별 상위 `hall_size`를 `ranking_hall`에 적재해 영구 보관한다.

**검토한 대안**
- Redis에 시즌 키를 계속 유지
- 회원별 역대 순위 테이블
- 백업 테이블 직접 조회

**이유**
- 확정된 순위는 정렬 구조가 필요 없어 Redis에 둘 이유가 없다.
- 회원별 역대 순위는 참가자 × 시즌만큼 행이 쌓여 일간 랭킹 기준 연간 수억 행이 될 수 있다.
- 백업 테이블 조회는 테이블 이름이 동적이라 데이터 경로에 동적 SQL이 들어간다.
- Top N은 시즌당 수십~수백 행이라 영구 보관 부담이 없다.

### D-49. 정산 결과를 `ranking_entry`에 함께 기록 — 확정

**결정:** `ranking_result`를 두지 않는다. 결과 컬럼(`final_rank`, `reward_code`, `reward_status`, `reward_held`, `sanctioned`, `delivered_at`)을 `ranking_entry`에 처음부터 두고, SETTLING은 시즌 파티션을 작업 테이블로 꺼내 가순위를 UPDATE한 뒤 같은 파티션으로 되돌린다. entry 시즌 파티션은 자기 시즌과 다음 시즌이 모두 SETTLED일 때 백업으로 분리한다. D-20을 대체하고 D-21, D-22의 일부를 바꾼다.

**배경:** 기존 설계는 시즌 종료 시 참가자 전원의 스코어를 result로 복사하고, 원본은 entry 백업으로 남겨 장기적으로 두 벌을 보관했다. 참가자가 많고 주기가 짧은 랭킹에서 저장 공간과 백업 크기가 두 배가 된다.

**검토한 대안**
- entry 백업만 SETTLED 시점에 삭제: 장기 이중 보관은 없어지지만 시즌마다 전원 복사 1회는 남는다.
- 작업 테이블에만 결과 컬럼을 ALTER로 추가: EXCHANGE는 컬럼·인덱스가 같아야 하므로 되돌리기 전에 다시 제거해야 한다. 데이터가 든 테이블의 컬럼 변경은 재구성이 될 수 있어 복사와 비용이 같다.
- 작업 테이블을 시즌 이름으로 RENAME해 결과로 사용: 보상·지난 시즌 조회가 동적 SQL이 되고(D-25), 전달이 끝나지 않으면 작업 테이블이 점유되어 다음 정산이 막힌다(D-47).

**이유**
- 복사가 한 번도 없고, 원본 스코어와 결과가 한 행에 남는다. 결과 계산은 `score`, `achieved_at`을 바꾸지 않으므로 원본 증거가 유지된다.
- 결과 컬럼을 처음부터 두면 작업 테이블은 `LIKE`로 항상 같은 구조라 정산 중 컬럼 DDL이 없다. 추가 저장 공간은 행당 몇 바이트다(NULL 컬럼은 비트, 기본값 0인 TINYINT 3개는 1바이트씩).
- 데이터 경로 SP는 여전히 고정 이름(`ranking_entry`)만 정적 SQL로 읽는다.

**감수할 것**
- 운영 테이블에 진행 중에는 쓰지 않는 컬럼과 결과 인덱스 2개가 붙는다. 제출은 결과 컬럼을 바꾸지 않으므로 인덱스 비용은 신규 멤버 INSERT 때만 든다.
- 끝난 시즌 파티션이 SETTLED 이후까지 운영 테이블에 남는다. 늦은 쓰기는 제출 SP의 시각 검사(4.1)로 막는다. 파티션을 지워 막던 이중 장치는 없어진다.
- 되돌리기 EXCHANGE는 `WITHOUT VALIDATION`을 쓰며, 다른 시즌 행이 없음을 PK 범위 조회로 먼저 확인한다.
- 결과 갱신이 `version`, `updated_at`을 건드리면 리컨실러가 변경분으로 오인하므로 바꾸지 않는다.

### D-52. 마지막 시즌의 entry는 자기 시즌 SETTLED로 분리 — 확정

**결정:** `ranking_entry` 분리 조건 "다음 시즌도 SETTLED"는 다음 시즌이 생길 수 없는 마지막 시즌에는 적용하지 않는다. 마지막 시즌은 다음 시즌 행이 없고, 랭킹이 반복 없음이거나 종료되었거나 랭킹 `end_at`이 그 시즌 `end_at` 이하인 시즌이다.

**배경:** 단일 이벤트, 종료된 랭킹의 마지막 시즌은 다음 시즌이 없어 조건을 영원히 만족하지 못하고, entry 파티션이 운영 테이블에 무기한 남는다.

**검토한 대안**
- 운영 테이블에 계속 보관: 랭킹당 하나라 쌓이지는 않지만, 끝난 랭킹의 데이터가 운영 테이블과 파티션 수를 계속 차지한다.
- 다음 시즌 행이 없으면 무조건 분리: 반복 랭킹에서 스케줄러가 다음 시즌 행을 늦게 만들면 직전 시즌 조회 대상이 일찍 빠진다.

**이유:** 다음 시즌 조건은 "다음 시즌이 진행되는 동안 직전 시즌 전체 순위를 운영 테이블에서 조회"하기 위한 것이다(8.5). 다음 시즌이 없으면 지킬 대상이 없다. 마지막 시즌의 조회는 hall(Top N)로 한다.

## 데이터베이스 운영

### D-24. 운영 테이블은 랭킹 간 공유 — 확정

**결정:** `ranking_entry`를 모든 랭킹이 공유하고, MDL 대기는 운영 규칙으로 대응한다.

**검토한 대안:** 랭킹별 테이블 (`ranking_entry_{rankingId}`).

**이유**
- 랭킹별 테이블은 MDL이 격리되지만, 데이터 경로 SP가 동적 SQL을 써야 한다.
- DDL 세션의 짧은 `lock_wait_timeout`, 운영 테이블 긴 쿼리 금지, 한가한 시간대 실행으로 다른 랭킹이 멈추는 시간을 최악 수 초로 제한할 수 있다.

### D-25. 모든 DB 로직은 SP, PREPARE는 SP_EXEC_DDL 하나 — 확정

**결정:** DB 로직은 SP로만 작성한다. 동적 SQL은 파티션 DDL에만 쓰며, `PREPARE`를 실행하는 SP는 `SP_EXEC_DDL` 하나로 한정한다.

**배경:** DBA 정책상 prepared statement 사용을 제한해 왔다.

**이유**
- MySQL은 DDL 식별자에 변수를 받지 않아 파티션 DDL에는 동적 SQL이 불가피하다.
- 실행 지점을 하나로 모으면 `DEALLOCATE` 누락(→ `max_prepared_stmt_count` 고갈)이 원천 차단되고, 실행 SQL 감사 로그를 한곳에서 남길 수 있다.
- 이름은 `INT UNSIGNED` 파라미터로만 조립해 인젝션 여지를 없앤다.
- 데이터 경로는 전부 정적 SQL이다.

**확인된 사실:** 동적 SQL이라고 인덱스를 못 타지는 않는다. 생성된 SQL은 일반 쿼리와 동일하게 최적화된다. 단점은 파싱 비용, 생성 시점 검증 불가, 인젝션 위험, 가독성이다.

### D-26. 테이블명 `rank` → `ranking_entry` — 확정

**이유:** `RANK`는 MySQL 8.0.2부터 예약어다. 매번 백틱이 필요하고 실수 여지가 크다.

### D-51. `SP_EXEC_DDL`은 SQL SECURITY INVOKER — 확정

**결정:** `SP_EXEC_DDL`만 `SQL SECURITY INVOKER`로 만든다. 다른 SP는 기본값(DEFINER)이다. 메인·로그 DB 모두 같다.

**배경:** 앱 계정은 스키마 단위 `EXECUTE`를 가지므로(D-44) 내부 헬퍼인 `SP_EXEC_DDL`도 직접 CALL할 수 있다. DEFINER면 migrate 계정 권한으로 임의 DDL이 실행되어, 앱 계정이 탈취되면 테이블을 지울 수 있다.

**검토한 대안**
- 앱 계정에 SP별로 `EXECUTE`를 부여하고 `SP_EXEC_DDL`만 제외: SP가 늘 때마다 권한을 관리해야 하고, 러너에 GRANT 권한이 필요하다.
- `SP_EXEC_DDL`이 허용 DDL 형식만 받도록 검사: 형식이 맞는 파괴적 DDL(데이터가 든 파티션 DROP)은 막지 못한다.

**이유:** INVOKER SP는 호출자 보안 문맥으로 실행된다. 관리 SP(DEFINER) 안에서 부르면 DEFINER 권한, 앱이 직접 부르면 앱 권한이라 감사 로그 INSERT부터 권한 오류(1142)로 실패한다. 로컬에서 두 경우 모두 확인했다.

## 외부 인터페이스와 보안

### D-27. x-api-key 인증 + 권한 분리 — 확정

**결정:** 서버 간 호출 전용 API 키. write / read / reward 권한을 분리하고, 관리 API는 GM 도구 인증으로 분리한다.

**검토한 대안:** HMAC 서명, mTLS.

**이유:** 싱글테넌트라 호출자가 해당 프로젝트 게임 서버로 한정된다. TLS와 IP 허용 목록을 전제로 하면 API 키로 충분하다. 공용 인터넷을 경유하는 배치일 때만 서명이나 mTLS를 고려한다.

### D-53. HTTP는 Fastify, Redis 클라이언트는 node-redis — 확정

**결정:** API 서버는 Fastify, Redis 클라이언트는 node-redis(v5)를 쓴다.

**검토한 대안:** Express, NestJS / ioredis.

**이유**
- Fastify: 요청 스키마 검증과 Swagger 문서화(개발 컨벤션 1장)가 같은 스키마에서 나온다. Express는 둘을 따로 붙여야 하고, NestJS는 이 규모에 비해 무겁다.
- node-redis: 클러스터, Lua(EVALSHA 자동 대체), 파이프라인 등 설계가 쓰는 기능을 모두 지원하고 Redis사가 공식으로 개발한다. ioredis는 기능은 같지만 유지보수가 최선 노력 단계이고 새 프로젝트에 node-redis를 권한다. 설치형 패키지로 오래 운영하므로 장기 지원을 택한다.

**감수할 것:** node-redis는 명령 단위 타임아웃 설정이 ioredis보다 불편하다. Redis 반영은 실패해도 응답이 성공(4.1)이라, 반영 호출 한 곳에서 타임아웃을 감싼다.

### D-54. API 키는 SHA-256 해시 저장, 메모리 목록으로 인증 — 확정

**결정:** `api_credential`에 키의 SHA-256 해시와 권한 비트를 둔다. API는 활성 키 목록을 메모리에 두고 30초마다 다시 읽는다. 발급·폐기는 CLI로 한다.

**검토한 대안:** bcrypt 해시, 요청마다 DB 조회, 짧은 TTL 캐시.

**이유**
- 키는 32바이트 난수라 무차별 대입이 불가능하다. 느린 해시는 비밀번호처럼 엔트로피가 낮은 값을 위한 것이다.
- 키는 설치본마다 몇 개뿐이라 전체 목록을 들고 있는 편이 단순하고, 제출 경로에 DB 왕복이 늘지 않는다.

**감수할 것:** 폐기·발급이 최대 30초 늦게 반영된다. 키 변경은 드물고 교체 절차로 피할 수 있으며, 긴급 시 재시작으로 즉시 반영한다.

**부가 결정:** 제출 API는 `requestId` 멱등 키를 받는다. SUM은 재시도 시 중복 가산되므로 필수다.

### D-28. Anti-cheat는 이상 징후 탐지 + 검수 연동 — 확정

**결정:** 하드 검증(거부), 소프트 탐지(표시), 어뷰징 포인트(근거 합산)로 구성한다. 자동 조치는 보상 보류까지만 한다.

**이유**
- 랭킹 서버는 스코어를 의미 없는 정수로 다루므로 플레이 정당성은 판단할 수 없다. 그것은 게임 서버의 책임이다.
- 통계적 이상은 오탐이 있으므로 거부하면 정상 유저가 피해를 본다.
- 포인트를 근거에서 계산해야 "왜 이 점수인가"에 답할 수 있다.
- 포인트는 검수 대상을 좁히는 지표이며 판정이 아니다.

**부가 결정:** 시즌 간 포인트는 합산하지 않고 참고로만 표시한다. 한 번의 오탐이 계속 불이익이 되지 않게 한다.

### D-50. 랭킹 정의 테이블 이름을 `ranking_definition`으로 변경 — 확정

## 1단계 구현 착수 시 결정

구현 착수 전 Claude Code의 확인 요청에 대한 결정이다.

### D-30. 제출 시 시즌 번호 필수 — 확정

**결정:** 스코어 제출은 `seasonNo`를 필수로 받는다. 게임 서버는 플레이 시작 시점의 시즌 번호를 보내고, 현재 OPEN 시즌과 다르면 `SEASON_MISMATCH`로 거부한다.

**배경:** 시즌을 넘는 멱등 재시도를 검토하다 발견했다. `wait_period = 0`이면 시즌 N 종료 직후 N+1이 열리므로, 시각 검사만으로는 시즌 N에서 시작한 플레이가 N+1에 반영된다. D-14의 엄격 마감이 다음 시즌이 열려 있는 경우에는 지켜지지 않는 빈틈이었다.

**검토한 대안**
- 시즌 번호 없이, 멱등 키를 현재 시즌에서 못 찾으면 직전 시즌 로그도 조회
- 시즌 번호를 선택값으로 받기

**이유**
- 게임 서버는 클라이언트에 시즌 정보(번호, 종료까지 남은 시간)를 보여줘야 하므로 어차피 시즌을 알고 있다.
- 플레이가 어느 시즌에 속하는지 명시되어 엄격 마감이 항상 지켜진다.
- 재전송은 같은 시즌 번호를 들고 오므로 멱등 조회가 해당 시즌 파티션 하나로 끝난다. 직전 시즌 조회 같은 우회가 필요 없다.
- 과거 시즌 번호는 시각 검사에서 거부되어 조작이 불가능하다.

### D-31. SUM 결과가 score_max를 넘으면 거부 — 확정

**검토한 대안:** `score_max`로 맞추기(클램프).

**이유:** `score_max`는 비트 예산의 경계다. 넘는다는 것은 정의가 잘못되었거나 비정상 제출이라는 신호이므로 조용히 맞추지 않고 거부한다. 거부 사유는 멱등 키(`rejected`)와 제출 이력에 남아 어뷰징 탐지 근거가 된다.

### D-32. SUM 첫 제출의 증분이 0 이하면 entry 행을 만들지 않음 — 확정

**이유:** 0점 행이 생기면 참가자 수와 Redis 순위표에 0점 유저가 들어가고, PERCENT 보상 구간의 분모가 틀어진다. 제출 자체는 로그에 남긴다.

**보완:** 처음에는 "음수면"이었으나, 증분 0도 같은 결과(0점 행)를 만들므로 "0 이하"로 넓혔다.

**응답:** 오류가 아니라 정상 처리다. `RESULT 0`과 `score = 0`, `version = 0`, `achieved_at = NULL`을 반환한다. 멱등 키는 기록한다. 재전송은 다른 경우와 같이 현재 entry 상태를 반환하며, 그때도 행이 없으면 같은 값을 반환한다. 앱은 `version = 0`이면 Redis 반영을 건너뛴다. 별도 실패 코드로 돌려주면 게임 서버가 실패로 보고 재시도한다.

### D-33. 멱등 키 충돌은 거부 — 확정

**결정:** 같은 `requestId`에 다른 내용(member, 값)이 오면 `IDEMPOTENCY_CONFLICT`로 거부한다.

**이유:** 이전 결과를 그대로 반환하면 게임 서버의 키 생성 버그가 조용히 묻힌다.

### D-34. 비 ACTIVE 랭킹은 제출 거부 — 확정

**이유:** 쓰기 차단은 시각으로 한다(D-11)는 원칙과 별개로, 관리자가 랭킹을 일시 중지(PAUSED)하거나 종료(ENDED)하면 즉시 반영되어야 한다.

### D-35. 개발 컨벤션과 설계의 충돌 처리 — 확정

**결정**

| 항목 | 따르는 쪽 |
| --- | --- |
| 컬럼·키 구조 (복합 PK, DATETIME(3)) | 설계 |
| 상태·구분값 컬럼 타입 | 컨벤션 — `TINYINT UNSIGNED` + COMMENT 매핑 (D-46) |
| 표기 규칙 (COMMENT, 헤더 주석, charset/collation, 인덱스 이름) | 컨벤션 |
| SP 이름 (대문자) | 컨벤션 |
| SP 결과 반환 | 컨벤션 RESULT 규약 (단, D-36) |
| 로그 테이블 위치 | `log_ddl_audit`는 메인 DB, 제출 이력은 로그 DB (D-48) |
| 식별자 컬럼 콜레이션 | `utf8mb4_bin` (`member_id`, `request_id`, `ranking_code`, `reward_code`, `rule_code`) |
| 락 헬퍼의 DB 접근 | SP 미사용, `GET_LOCK` 직접 호출 (컨벤션 예외) |

**이유**
- 파티션 테이블은 파티션 키가 PK에 포함되어야 하므로 대리키 기반 컨벤션을 그대로 적용할 수 없다.
- 설계 문서의 소문자 SP 이름은 설명용이었다. 이름 규칙은 기존 컨벤션이 기준이다.
- `log_ddl_audit`는 `SP_EXEC_DDL` 안에서 기록해야 하므로 물리 분리할 수 없다. 제출 로그는 멱등 키와 이력으로 나눠 이력만 분리한다 (D-48).
- 식별자는 대소문자를 구분하지 않으면 `UserA`와 `usera`가 같은 member로 합쳐진다.
- 러너는 SP가 생성되기 전에도 락을 잡아야 하므로 락 헬퍼는 SP를 거칠 수 없다.

### D-36. SP 오류 처리: 내부 헬퍼는 RESIGNAL — 확정

**결정:** `SP_EXEC_DDL`은 실패 시 감사 로그를 기록하고 `RESIGNAL`한다. 앱이 호출하는 SP는 RESULT 규약을 따르며, 관리 SP는 헬퍼의 예외를 받아 `50001`로 반환한다.

**검토한 대안:** 헬퍼까지 RESULT 규약 적용.

**이유:** 헬퍼가 RESULT를 SELECT하면 호출한 SP에서 결과셋이 이중으로 나간다. 내부 헬퍼는 예외로 실패를 알리고, 앱과의 경계에서만 규약으로 변환한다.

### D-37. 마이그레이션: 테이블은 버전, SP는 반복 — 대체됨 (실행 방식은 D-39)

**결정:** 테이블은 버전 마이그레이션, SP는 체크섬이 바뀌면 DROP 후 CREATE하는 반복 마이그레이션으로 관리한다. 통합 SQL 파일은 두지 않는다.

**이유:** 버전 체계와 통합 파일을 함께 두면 같은 내용을 두 곳에서 관리하게 된다. 설치형 배포는 기동 시 자동 적용이 필요하므로 러너가 기준이다.

**대체 내용:** 파일 관리 방식(테이블은 버전, SP는 반복, 통합 파일 없음)은 유지한다. "기동 시 자동 적용"은 D-38, D-39로 대체되었다.

## 배포와 운영

### D-38. DB 변경이 있는 배포는 중단 패치 — 확정

**결정:** 앱 코드만 바뀌는 배포는 롤링으로, DB(테이블, SP) 변경이 있는 배포는 전체 중지 → migrate → 기동으로 한다. 게임 점검 시간에 맞추는 것을 원칙으로 한다.

**배경:** 기동 시 자동 마이그레이션(D-37)을 스케일아웃 환경의 롤링 배포에서 검토했다. 문제는 다음과 같았다.
- MySQL 8.4에는 `CREATE OR REPLACE PROCEDURE`가 없어 SP를 바꾸는 DROP과 CREATE 사이에 호출이 실패한다.
- 구버전 인스턴스가 바뀐 스키마·SP를 그대로 사용한다.
- 반복 마이그레이션이 구버전 인스턴스 재시작으로 SP를 구버전 본문으로 되돌린다.
- 공유 운영 테이블의 DDL이 MDL 대기에 걸리면 모든 랭킹의 쓰기가 멈춘다.

**검토한 대안:** 무중단 마이그레이션 (배포 전 migrate 1회, expand/contract, 시그니처 변경 SP는 `_V2` 새 이름, 본문 수정은 1305 에러 재시도로 공백 흡수, 운영 테이블은 INSTANT DDL만)

**이유**
- 위 대안으로도 공유 테이블 DDL의 짧은 정지, INSTANT가 아닌 변경, backfill, 롤백 제약(contract 이후 불가), Redis·API 호환은 남는다. 무중단은 러너 하나로 보장되지 않고 변경 규칙과 배포 절차 전체가 필요하다.
- 게임은 정기 점검이 있는 도메인이다. 게임이 내려가 있으면 스코어 제출이 없으므로 랭킹 서버 중지의 영향이 없다.
- 중단 패치에서는 구버전·신버전이 공존하지 않으므로 expand/contract, SP 버전 이름, 재시도 같은 장치가 모두 필요 없어진다.
- 시즌 마감은 시각, 정산·아카이브는 상태 관측 기반이라 중단 후 기동하면 밀린 단계부터 이어간다.

**남긴 원칙:** 운영 테이블 대량 backfill 금지, INSTANT가 아닌 변경은 소요 시간을 측정해 점검 시간 안에 끝나는지 확인.

### D-39. 기동 시에는 마이그레이션을 확인만 — 확정

**결정:** 적용은 `npm run migrate`로만 한다. API와 워커는 기동 시 스키마(SQL 파일 목록·체크섬)가 패키지와 다르면 기동을 거부한다. `migrate`는 살아 있는 인스턴스 하트비트가 있거나, 역행 검사(미지의 테이블 버전 파일, 낮은 package version)에 걸리면 실행을 거부한다.

**이유**

| 실수 | 차단 |
| --- | --- |
| 인스턴스를 내리지 않고 migrate | 하트비트 검사 |
| migrate 없이 새 버전 기동 | 기동 시 스키마 확인 |
| DB 변경 패키지를 실수로 롤링 배포 | 기동 시 스키마 확인으로 데이터 안전은 항상 보장. 구버전 유지(가용성)는 실패한 배포를 멈추는 도구일 때만 성립하며 pm2는 해당하지 않음 (아래 보완) |
| migrate 하트비트 검사 직후 구버전 기동 | 기동·migrate가 같은 락 사용, 기동은 하트비트를 락보다 먼저 기록 |
| 구버전 패키지로 migrate (테이블 변경 포함) | 미지의 테이블 버전 검사 |
| 구버전 패키지로 migrate (SP만 변경) | package version 역행 검사 |

- 자동 적용으로 두면 DB 변경 패키지를 롤링 배포했을 때 첫 인스턴스가 마이그레이션을 실행해 D-38의 문제가 그대로 발생한다.
- 하트비트 검사에는 강제 실행 옵션을 두지 않는다. "급하니 일단 실행"이 되면 장치의 의미가 사라진다. 비정상 종료한 인스턴스의 하트비트는 30초 후 만료된다.
- 하트비트로 판단하므로 프로세스 관리 방식(pm2, systemd, Docker)과 무관하게 동작한다.

**보완 (1단계 구현 체크 후)**
- **롤링 시 보장 범위 (pm2 실험 후 정정):** 처음에는 "헬스체크를 기다리는 롤링이면 배포가 멈추고 구버전이 계속 서비스한다"고 보았으나, 보장을 둘로 나눠야 했다.
  - 데이터 안전(틀린 스키마로 서비스하지 않음)은 기동 시 스키마 확인으로 도구와 무관하게 성립한다.
  - 가용성(구버전 유지)은 실패한 배포를 멈추는 도구일 때만 성립한다. pm2는 `--wait-ready`를 써도 `listen_timeout` 후 구버전을 내려 약 32초 뒤 전체 중단되었고, fork 모드 reload는 즉시 재시작했다.
  - 결론: DB 변경 패키지에는 pm2 reload를 금지하고 `upgrade`만 사용한다. Kubernetes RollingUpdate처럼 진행을 멈추는 도구는 가용성까지 기대할 수 있으나 검증 전이다.
- **migrate 직후 구버전 기동 빈틈:** migrate가 하트비트 검사를 통과한 직후 구버전 패키지가 기동하면, 구 스키마와 일치해 확인을 통과하고 하트비트도 아직 없어 검사에 보이지 않았다. 감수하지 않고 막았다. 기동은 하트비트 기록 → 락 → 스키마 확인 순서로, migrate는 락 → 하트비트 검사 → 적용 순서로 실행한다. 어느 쪽이 락을 먼저 잡아도 한쪽이 거부된다. 비용은 기동 시 짧은 락 하나뿐이다.
- **버전의 정의:** 기동 시 확인은 버전 번호가 아니라 SQL 파일 목록·체크섬 비교다. migrate 역행 검사는 DB에 기록된 `package.json` version과 비교한다. 사람이 version을 올리는 규칙에만 의존하지 않도록, DB에 적용 기록이 있는데 패키지에 없는 테이블 버전 파일이 있으면 자동으로 거부한다. SP만 바뀐 경우는 파일로 신구를 구분할 수 없어 version 규칙에 의존한다.
- **하트비트 정리:** `instance_id`는 PID 대신 기동마다 생성하는 UUID다(PID 재사용으로 다른 인스턴스 행을 덮어쓰는 것 방지). 비정상 종료로 남은 행은 하트비트 루프가 1시간 넘은 것을 삭제한다.

### D-40. upgrade 스크립트는 환경 명령 주입 방식 — 확정

**결정:** `npm run upgrade`가 중지 → 하트비트 소멸 대기 → migrate → 기동 → 새 버전 하트비트 확인을 수행한다. 중지·기동 명령은 `UPGRADE_STOP_CMD`, `UPGRADE_START_CMD` 환경 변수로 받는다.

**배경:** 프로세스 중지·기동 방식이 배포 환경마다 달라 Docker 작업 때로 미루려 했다.

**이유**
- 환경에 따라 달라지는 것은 명령뿐이므로, 명령을 주입받으면 스크립트 자체는 지금 확정할 수 있다. Docker 도입 시 값만 바꾼다.
- 마지막 단계에서 기대 구성(API 수, 워커 수)만큼 새 버전 하트비트를 확인해 "올렸는데 실제로는 안 떴다"는 상황을 잡는다.

### D-41. GET_LOCK은 전용 커넥션, 청크마다 보유 확인 — 확정

**결정:** 락 헬퍼는 풀에서 전용 커넥션을 받아 작업이 끝날 때까지 반납하지 않는다. 장시간 잡은 청크마다 `IS_USED_LOCK(name) = CONNECTION_ID()`로 락 보유를 확인하고, 아니면 중단한다.

**배경:** 워커 스케일아웃 시 정산 등 잡의 단일 실행을 검토했다.

**이유**
- `GET_LOCK`은 커넥션에 묶인다. 풀에 반납하면 다른 코드가 그 커넥션을 쓰면서 락이 엉뚱하게 유지되거나 풀린다.
- 커넥션 단절이나 MySQL 페일오버 시 락이 풀려, 첫 워커가 작업 중인데 다른 워커가 같은 잡을 시작할 수 있다. 단계가 멱등이고 PK가 중복을 막아 데이터가 깨지지는 않지만, 겹치는 상황 자체를 줄인다.

**확인된 사실:** 워커 스케일아웃은 잡 처리량이 아니라 가용성을 위한 것이다. 잡은 항상 한 곳에서만 돈다.

### D-42. Redis 반영은 센티넬이 있을 때만 — 확정

**결정:** 모든 Redis 반영 Lua는 시즌 센티넬(`:ready`)이 있을 때만 쓴다. 센티넬은 시즌 OPEN 시 설정하고, 정산의 키 삭제는 센티넬부터 지운다.

**배경:** API 스케일아웃 시, MySQL 커밋 후 Redis 반영 재시도가 정산의 시즌 키 삭제보다 늦게 도착하는 경우를 검토했다.

**이유**
- 늦은 반영이 지운 시즌 키를 멤버 몇 명으로 되살리고, 그 키는 아무도 지우지 않아 메모리에 영원히 남는다. 인스턴스가 많을수록 확률이 커진다.
- 정산 결과는 MySQL 기준으로 만들어지므로 늦은 반영을 버려도 손실이 없다.
- 재구축용으로 이미 있던 센티넬을 쓰기 허용 조건으로 확장한 것이라 새 장치가 필요 없다. BEST도 조건 확인을 위해 Lua로 반영한다.

### D-43. 멱등 재전송은 현재 entry 상태를 반환 — 확정

**결정:** 같은 `requestId`, 같은 내용의 재전송은 반영하지 않고 처리 당시 결과가 아닌 현재 entry 상태를 `replayed = 1`과 함께 반환한다.

**이유**
- 앱은 응답으로 Redis를 반영한다. 처리 당시 값을 돌려주면 그 사이 다른 제출로 version이 올라간 경우 오래된 값을 반영하려다 거부되거나, 반영 경로가 낡은 값을 기준으로 움직인다. 최신 행이어야 version 비교가 맞게 동작한다.
- 멱등 키에는 처리 당시의 달성 시각과 version을 보관하지 않으므로, 당시 결과를 완전히 재현하려면 로그 컬럼을 늘려야 한다.
- 게임 서버 입장에서도 재시도의 목적은 "반영되었는가, 지금 점수는 얼마인가"이므로 현재 상태가 더 유용하다.

### D-44. DB 계정 분리: migrate 계정과 앱 계정 — 확정

**결정:** `podium_migrate`는 `podium_de` 전체 권한과 `PROCESS`를 가지며 SP의 DEFINER가 된다. `podium_app`은 `EXECUTE`만 가진다. API·워커는 앱 계정으로, `migrate`·`upgrade`는 migrate 계정으로 접속한다.

**이유**
- 모든 DB 로직이 SP이므로(D-25) 앱 계정은 실행 권한만 있으면 된다. 앱 계정이 탈취돼도 테이블을 직접 읽거나 고칠 수 없다.
- SP는 `SQL SECURITY DEFINER`라 DEFINER 권한으로 실행된다. 정산 전 `INNODB_TRX` 조회(7.1)에 필요한 `PROCESS`도 DEFINER인 migrate 계정이 가진다.
- API·워커만 도는 호스트에는 migrate 계정 정보를 두지 않는다.

**예외:** 락 헬퍼의 `GET_LOCK`(D-41)은 권한이 필요 없어 앱 계정으로 직접 호출한다.

**절차:** [03_DEV_SETUP 3.1](03_DEV_SETUP.md#31-스키마와-계정-생성)

### D-45. 시즌 주기는 초 단위 고정 길이까지 허용, 하한 없음 — 확정

**결정:** `cycle_type`의 `DAYS`를 `FIXED`(`cycle_value`초)로 바꾼다. 최소 주기는 두지 않고, `정산 시작 지연 + review_period`가 시즌 길이 안에 들어가지 않으면 등록을 거부한다. 정산 시작 지연은 `max(settle_delay, 리컨실러 안전마진 + 리컨실러 실행 주기)`다. `wait_period`는 제한하지 않는다.

**검토한 대안:** `HOURS` 추가, 환경 변수 하한(`MIN_CYCLE_SEC`), 코드 고정 하한, `wait_period < 시즌 길이` 조건.

**이유**
- 운영상 쓸 일은 드물지만, 하루 안에 여러 번 도는 이벤트 같은 최악의 경우를 스키마 변경 없이 받기 위해서다. 단위를 초 하나로 통일하면 DAYS·HOURS·MINUTES를 따로 둘 필요가 없다.
- 짧은 주기의 실제 위험은 정산 적체다. 이를 시간 조건으로 등록 시점에 막는다.
- 정산은 `settle_at`뿐 아니라 리컨실러 워터마크 조건(7.1)도 만족해야 시작하므로, `settle_delay`만으로 계산하면 짧은 주기에서 실제 시작이 더 늦어 적체를 막지 못한다.
- `wait_period`는 시즌 사이의 공백이라 정산과 겹치지 않는다. 제한하면 "7일 시즌을 한 달에 한 번" 같은 설정이 막힌다.

**감수할 것:** 주기가 매우 짧으면 공유 운영 테이블에 파티션 DDL이 자주 걸린다(11.1). 하한은 운영 판단에 맡긴다.

### D-46. 상태·구분값은 ENUM 대신 TINYINT 코드 + const — 확정

**결정:** 상태·구분값 컬럼은 `TINYINT UNSIGNED`로 저장한다. 값의 의미는 `src/codes.ts`의 const에서만 관리하고, 컬럼 COMMENT에 코드→의미 매핑과 const 이름(`[codes.SeasonStatus]` 등)을 적는다. SP는 같은 숫자를 리터럴로 쓴다. D-35의 "ENUM은 설계를 따름"을 대체한다.

**대상:** `ranking_def`(status, update_rule, sort_order, time_unit, cycle_type), `ranking_reward_tier.range_type`, `ranking_season.status`, `ranking_entry.reward_status`(D-49 이전 `ranking_result`). 이미 숫자였던 `log_ddl_audit.status`, `instance_heartbeat.process_type`과 관리 SP의 파티션 대상 코드도 같은 파일에서 관리한다.

**이유**
- 개발 컨벤션 16.1(상태값은 TINYINT + COMMENT 매핑)과 맞춘다.
- ENUM은 값 추가·순서 변경이 테이블 정의 변경이라 운영 테이블에 DDL이 필요하다. 코드는 const와 COMMENT만 고치면 된다.
- 앱과 SP가 같은 숫자를 쓰고 의미를 한 곳에서 관리한다.

**규칙**
- 이미 저장된 값의 의미는 바꾸지 않는다. 새 의미는 새 번호로 추가한다.
- "없음"을 뜻하는 값은 0(`CycleType.NONE`, `RewardStatus.NONE`), 그 외는 1부터 쓴다.
- `SeasonStatus`는 진행 순서대로 번호를 매겨 크기 비교로 단계를 판단할 수 있게 한다.

### D-47. 전달 미완료 시즌은 기한 없이 보관, GM 강제 종료만 허용 — 확정

**결정:** DELIVERING 시즌은 PENDING이 모두 ack될 때까지 운영 테이블에 둔다. 결과를 담은 테이블(D-49 이후 `ranking_entry`)은 자기 시즌과 다음 시즌이 모두 SETTLED일 때만 백업으로 분리한다. ack 정체와 DELIVERING 적체는 알림으로 알리고, 포기는 GM 강제 종료(`forced_by`, `forced_reason` 기록)로만 한다.

**배경:** 게임 서버 연동이 한 시즌 넘게 장애이면, 기존 "다음 시즌 SETTLED 시 분리" 조건으로는 다음 시즌이 먼저 끝났을 때 전달 중인 시즌의 result가 백업으로 빠져 남은 PENDING을 조회할 수 없었다.

**검토한 대안**
- 보상 API가 백업 테이블도 조회: 테이블 이름이 시즌마다 달라 동적 SQL이 필요하다 (D-23, D-25 위배).
- 일정 기간 후 자동 포기: 랭킹 서버가 보상을 버리는 경로가 생긴다. 자동으로 해결되지 않으면 멈추고 알린다는 원칙(01_DESIGN 1.5)에 어긋난다.

**감수할 것:** 장애 동안 해당 시즌 파티션이 운영 테이블에 남는다. 짧은 주기 랭킹은 파티션 상한(8192)에 다가갈 수 있어 적체 알림으로 대응한다.

### D-48. 제출 로그를 멱등 키(메인 DB)와 이력(로그 DB)으로 분리 — 확정

**결정:** 제출 로그를 나눈다. 멱등 판별에 필요한 최소 컬럼은 메인 DB `ranking_submit_key`에 두어 반영과 같은 트랜잭션에서 기록한다. 전체 이력은 로그 DB `podium_de_log.log_ranking_submit`에 커밋 후 별도로 기록한다. 첫 라이브 전에 적용한다.

**배경:** 제출 로그는 제출마다 쌓이는 가장 큰 테이블이다. 메인 DB에 두면 로그 문제가 서비스 장애로 번진다.

**이유 (라이브 운영 관점)**
- 장애 격리: 로그 정리 실패나 디스크 포화가 제출·정산·보상을 멈추지 않는다.
- 복구 시간: 메인 DB 크기가 로그에 끌려가지 않아 백업·복구가 빠르다.
- 사람의 임의 조회: 조사용 조회가 공유 운영 테이블에 MDL과 부하를 주지 않는다.
- 로그 스키마 변경이 메인 운영 테이블 DDL이 되지 않는다.
- 분리는 운영 데이터가 없을 때 가장 싸다. 라이브 후에는 설치본마다 진행 중 시즌의 멱등 키 전환이 필요하다.

**검토한 대안:** 메인 DB 유지 후 부하 테스트로 판단. 성능 기준으로는 타당하지만 장애 격리와 전환 비용을 고려하지 않았다.

**부가 결정**
- 제출 이력은 결과와 무관하게 모든 제출을 `result_code`로 남긴다(빈도 초과, 비활성, 시즌 불일치, 충돌, 재전송 포함).
- 로그 DB 보관은 날짜 기준 일 파티션이며, 데이터가 찬 파티션을 DROP한다(서비스 경로가 아님). 파티션 DDL을 위해 로그 DB에도 `SP_EXEC_DDL`과 그 감사 로그 `log_ddl_audit`를 하나씩 둔다 — "PREPARE는 `SP_EXEC_DDL`에만"은 DB마다 하나로 적용한다. 로그 DB 파티션 이름은 `DATE` 파라미터로만 조립한다.
- 기동 시 로그 DB가 접속 불가면 경고 후 기동하고, 접속되는데 스키마가 다르면 기동을 거부한다.
- 로그 DB 접속 정보와 계정은 메인과 별도로 필수로 받는다(`DB_LOG_HOST`, `DB_LOG_PORT`, `DB_LOG_NAME`, `DB_LOG_APP_*`, `DB_LOG_MIGRATE_*`). 비었을 때 메인 값으로 대체하면 설정 누락이 조용히 로그를 메인 인스턴스에 쌓아 장애 격리를 무너뜨린다. 누락은 기동을 막고, 접속 장애는 경고만 한다.

**감수할 것:** DB, 커넥션 풀, 쓰기 경로가 하나씩 늘어난다. 로그 DB 장애 시 이력이 빠질 수 있다. 정산·검수에 필요한 `rejected`는 메인에 남겨 이력 유실이 정산에 영향을 주지 않게 한다.
