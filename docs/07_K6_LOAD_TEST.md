# 1. 요약

> **결론: API 1대는 제출 초당 1,000건까지 여유, 1,500건이 안정 한계, 2,200건이 붕괴점이다.**
>
> - **운영 목표: 1대당 평시 1,000건/초 이하로 유지**
> - **1,000건/초 또는 p99 100ms를 넘으면 증설 경보** — 이번 k6 측정에서 1,500건/초의 p99가 95.8ms로 경보선에 닿았다
> - **1,500건/초를 넘으면 위험** — 지연이 급증하는 구간
> - **2,200건/초가 물리 상한** — 더 보내도 처리량은 늘지 않고 지연만 초 단위로 늘어난다
> - **피크 2,300건/초 → API 3대 (N+1)**

## 1.1 API 1대 운영 기준표

| 구간 | 제출 (건/초, 1대) | 실측 지연 | 상태 | 할 일 | 근거 |
|---|---|---|---|---|---|
| 여유 | ~1,000 | p50 3.7ms, p99 20ms | 정상 | 없음 | 기존 측정 단계 상승, k6 3회(p50 3.7~3.9ms, p99 22~49ms) |
| 안정 한계 | 1,000~1,500 | p50 4~8ms, p99 38~155ms | 처리는 되지만 꼬리 지연이 100ms 안팎으로 출렁임 | **증설 경보.** 대수 추가 준비 | 기존 측정 3회, k6 1회(p99 95.8ms) |
| 위험 | 1,500~2,200 | 2,000에서 p50 173ms, p99 304ms | 유입이 처리보다 빨라 대기열이 쌓인다 | **즉시 증설** | 기존 측정 단계 상승. 오래 켜 둔 PC에서는 1,600~1,690건/초에서 포화(5.3) |
| 붕괴 | 2,200~ | p50 1.8s 이상 | 처리량이 약 2,200에서 멈추고 요청이 밀린다 | 장애 대응. 유입 차단 또는 긴급 증설 | 기존 측정 단계 상승 |

조회(top·member)는 3,000건/초에서도 p99 6ms 이하라 제출보다 훨씬 가볍다. 대수 산정은 제출만 기준으로 한다.

## 1.2 대수 산정

**필요 대수 = ⌈피크 제출 ÷ 1,500⌉ + 1**

1대가 장애나 배포로 빠져도 남은 서버들이 1대당 1,500건/초를 넘지 않게 하는 계산이다.

| 피크 (건/초) | 대수 | 평시 1대당 | 1대 빠졌을 때 1대당 |
|---|---|---|---|
| 1,000 | 2 | 500 | 1,000 |
| 2,300 (현재 추정) | **3** | 767 | 1,150 |
| 3,000 | 3 | 1,000 | 1,500 (한계) |
| 4,500 | 4 | 1,125 | 1,500 (한계) |

단일 PC에서 잰 값이라 하한 참고치다. 분리 환경에서 다시 재면 1대 상한은 더 올라갈 가능성이 크다(1.4의 3번).

같은 PC·같은 코드에서도 PC 상태에 따라 1대 상한이 약 1,600~2,000건/초로 출렁였다(5.3). 기준을 1,500에 두면 이 변동을 흡수한다.

**대수별 수용량과 근거** (서버를 각각 따로 둘 때)

| 대수 | 안정 (1,500×N) | 1대 빠져도 안정 (N+1) | 근거 |
|---|---|---|---|
| 1 | 1,500 | — | 실측 |
| 2 | 3,000 | 1,500 | 실측 (같은 PC에서 3,000건/초 처리, 5.4) |
| 3 | 4,500 | 3,000 | 추정. API는 1대 실측 × 3, MySQL은 4,000 커밋/초까지만 확인(5.4) |
| 4 | 6,000 | 4,500 | 추정. MySQL이 측정 범위 밖 |
| 5 | 7,500 | 6,000 | 추정. MySQL이 측정 범위 밖 |

4대 이상을 근거로 쓰려면 분리 환경에서 MySQL을 단독으로 6,000~7,500 커밋/초까지 재야 한다.

# 3. k6 기초

k6는 Grafana Labs의 오픈소스 부하 테스트 도구다. 엔진은 Go 실행 파일 하나이고 시나리오는 JavaScript로 쓴다.

- **설치만 되고 상주하지 않는다.** `k6 run`을 실행할 때만 프로세스가 뜨고, 끝나면 종료된다. 서비스·포트 점유가 없다.
- **Node가 아니다.** 스크립트에서 npm 모듈이나 이 프로젝트의 `src` 코드를 import할 수 없다. 그래서 DB 픽스처와 정합 검증은 `load.mjs`가 맡는다.

| 용어 | 의미 |
|---|---|
| VU (가상 사용자) | 시나리오 함수를 반복 실행하는 동시 실행 단위. VU마다 HTTP 연결을 따로 쓴다 |
| iteration | 시나리오 함수 1회 실행. 이 스크립트에서는 제출 요청 1건 |
| executor | 부하를 거는 방식. `constant-arrival-rate`는 초당 요청 수를 고정한다(서버가 느려져도 부하가 줄지 않음, load.mjs와 같은 방식). `constant-vus`는 VU 수를 고정한다 |
| check | 응답 검증(예: status 200). 실패해도 테스트는 계속된다 |
| threshold | 합격 기준(예: `p(99)<100`). 하나라도 넘으면 종료 코드가 0이 아니다 |
| `setup()` | 테스트 시작 시 한 번 실행. 반환값이 모든 VU에 전달된다 |
| `open()` | 시작 단계에서 로컬 파일을 읽는다. 키 파일을 읽는 데 쓴다 |


- 오래 멈춰 있으면 GitHub `grafana/k6` Releases에서 `windows-amd64.msi`를 받아 설치해도 된다.
- 제거: `winget uninstall k6`

## 4.4 첫 실행 — 낮은 부하로 동작 확인

```powershell
k6 run -e KEYS_FILE="$env:TEMP\podium-load.keys" -e RATE=100 -e DURATION=10s loadtest/k6-submit.js
```

- `-e 이름=값`은 스크립트의 `__ENV.이름`으로 들어간다. 키 원문은 명령줄에 쓰지 않고 파일 경로만 넘긴다.
- 실행 중 진행 줄 `000/200 VUs ... 100.00 iters/s`: 앞은 지금 일하는 VU 수, 뒤는 실제 초당 요청 수다.

결과(2026-10-08):

```
  █ THRESHOLDS
    http_req_duration
    ✓ 'p(50)<10' p(50)=3.25ms
    ✓ 'p(99)<100' p(99)=6.99ms
    http_req_failed
    ✓ 'rate<0.001' rate=0.00%

    http_req_duration..: avg=3.5ms p(50)=3.25ms p(95)=4.82ms p(99)=6.99ms max=18.42ms
    http_reqs..........: 1001   100.063808/s
    vus................: 1      min=0  max=1
```

## 4.5 요약표 읽는 법

| 항목 | 읽는 법 |
|---|---|
| THRESHOLDS ✓/✗ | 합격 기준 통과 여부. ✗가 하나라도 있으면 마지막에 `ERRO ... thresholds ... have been crossed`가 나오고 종료 코드가 0이 아니다 |
| `checks_succeeded` | `status 200` 검증 성공 비율. 100%가 아니면 실패 응답이 있었다 |
| `http_req_duration` | 요청 응답 시간. p50은 절반, p95는 95%, p99는 99%의 요청이 그 시간 안에 끝났다는 뜻이다 |
| `http_req_failed` | 4xx·5xx 응답 비율 |
| `http_reqs` | 보낸 요청 수와 초당 값. 목표 RATE와 같으면 부하를 제대로 걸었다. 0초와 끝 시점에 모두 발사하므로 1건 더 나올 수 있다(1,000 → 1,001) |
| `vus` max | 동시에 일한 VU 최대 수. 서버가 느려질수록 올라간다(포화 신호) |
| `dropped_iterations` | VU가 모자라 제때 못 보낸 요청 수. 크면 `maxVUs`를 늘리거나 서버가 포화된 것이다 |
| `iteration_duration` | 요청 시간 + 스크립트 처리 시간. `http_req_duration`과 차이가 작으면 k6 쪽 부담이 작다 |

## 4.6 정합 검증


| 항목 | 의미 |
|---|---|

# 6. 발견 사항

## 6.1 requestId 재사용 → 멱등 충돌

- 처음 스크립트는 `requestId`를 `k6-${__VU}-${__ITER}`로 만들었다. 이 두 값은 **실행마다 1과 0부터 다시 센다.**
- 1번 실행이 VU 1개로 `k6-1-0`~`k6-1-1000`을 썼고, 2번 실행의 VU 1이 같은 ID를 다른 회원·점수로 다시 보냈다. 서버는 정확히 1,001건을 1104(멱등 충돌)로 거절했다.
- 수정: `setup()`이 실행마다 시각 기반 접두어를 만들고, 번호는 테스트 전체에서 고유한 `exec.scenario.iterationInTest`를 쓴다 → `k6-<접두어>-<번호>`.
- 연동하는 게임 서버도 같은 실수를 할 수 있다. requestId는 재시도일 때만 같고, 새 요청이면 반드시 새 값이어야 한다.

## 6.2 p50이 기존 측정보다 높다

- 꼬리(p95·p99)는 기존 측정 범위 안인데 중앙값만 약 3ms 높다.
- 후보 원인: k6는 VU마다 연결을 따로 열고(최대 146개) Go 엔진이 여러 코어를 써서, 같은 PC의 API(Node)와 CPU를 다툰다.
- 측정 방식도 다르다. load.mjs는 예정 발송 시각부터, k6는 실제 발송 시각부터 잰다. 이번 실행은 drop 0이라 차이는 작다.
- 이 측정으로는 원인을 구분하지 못했다. 생성기를 다른 머신으로 옮기면 확인된다.
