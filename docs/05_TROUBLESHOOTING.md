# 장애 대응과 문제 해결 기록

1장은 운영 중 증상에서 원인과 조치를 찾는 표, 2장은 개발 중 실제로 겪은 문제와 해결 기록이다.
로그는 log4js 파일(`<filename>.<api|worker|migrate>[.인스턴스]`)에 남고, 요청은 `x-request-id`로 두 줄(`-->`, `<--`)을 찾는다.

# 1. 운영 장애 대응

## 1.1 기동·배포

| 증상 (로그) | 원인 | 조치 |
|---|---|---|
| `실행 중인 인스턴스가 있어 migrate를 거부합니다` | 최근 30초 안에 하트비트가 있는 인스턴스가 있다 | 출력된 인스턴스를 모두 정상 종료한 뒤 다시 실행. 강제 종료(kill, Windows `Stop-Process`)한 인스턴스는 행이 남으므로 30초 뒤 다시 실행 |
| `DB 스키마가 앱과 다릅니다. npm run migrate가 필요합니다` (기동 거부) | 패키지의 SQL 파일과 DB 적용 기록이 다르다 | 전체 중지 → `npm run migrate` → 기동 (중단 패치, 01_DESIGN 11.5) |
| `스키마 확인용 락(podium:migrate)을 10초 안에 얻지 못했습니다` | migrate가 실행 중이다 | migrate 종료를 기다린 뒤 기동 |
| `DB에 더 높은 버전(x.y.z)이 적용되어 있습니다` | 낮은 버전 패키지로 migrate를 실행했다 | 올바른 버전 패키지로 실행. DB를 되돌리는 경로는 없다 |
| `이미 적용된 마이그레이션이 변경되었습니다` | 적용된 테이블 파일(`V0xx`)을 고쳤다 | 파일을 원래대로 돌리고 변경은 새 `V` 파일로 추가 |
| `SP_xxx이(가) DB에 없습니다. npm run migrate가 필요합니다` | 미적용 DB | `npm run migrate` |
| `로그 DB(...) 접속 설정이 잘못되었습니다` | `DB_LOG_*` 계정·DB 이름 오류(1044/1045/1049) | 환경 변수 확인. 네트워크 수준 실패면 경고만 남기고 기동한다 |
| `no active api credential — all requests will be rejected` | 활성 API 키가 없다 | `npm run credential -- create <이름> <권한>` |
| upgrade `[2/5 wait stop] ... 멈추지 않았습니다` | 중지 명령 후에도 하트비트가 남았다 | 남은 인스턴스를 확인해 중지. 비정상 종료면 30초 뒤 재실행 |

## 1.2 API 응답

| result / HTTP | 의미 | 게임 서버 조치 |
|---|---|---|
| 1101 / 404 | 없는 랭킹. 새로 등록한 랭킹은 최대 30초 뒤부터 보인다 (D-56) | ID 확인, 등록 직후면 잠시 후 재시도 |
| 1102 / 409 | 운영 중(ACTIVE)이 아닌 랭킹 | 랭킹 상태 확인 |
| 1103 / 409 | 현재 시즌이 아니다 (시즌 경계, 잘못된 `seasonNo`) | 현재 시즌을 다시 조회. 같은 `requestId` 재시도로는 해결되지 않는다 |
| 1104 / 409 | 같은 `requestId`로 다른 내용이 이미 제출됐다 | 제출마다 새 `requestId`를 만드는지 확인 |
| 1105 / 1106 / 1107 (400) | 스코어 범위, 1회 증분(`max_delta`), 누적 상한(`score_max`) 초과 | 값 확인. SUM은 `max_delta`를 먼저 검사한다 |
| 2006 / 429 | 분당 제출 한도 초과 | 잠시 후 같은 `requestId`로 재시도 |
| 2005 / 503 | 처리 시간 초과. 서버에서는 반영됐을 수 있다 | 같은 `requestId`로 재시도 (반영됐으면 `replayed: true`) |
| 50001 / 500 | DB 시스템 오류 | 같은 `requestId`로 재시도. 서버 로그의 `DB 오류 <errno> (<sqlstate>)`로 원인 확인 |
| 1301 / 404 | 지금 시각에 해당하는 시즌이 없다 (시즌 사이 공백, 종료된 랭킹) | `seasons/current`로 확인. 시즌이 생성됐는지(스케줄러) 확인 |
| 2007 / 503 | 순위표를 쓸 수 없다: 센티넬 없음(OPEN 전, 재구축 중) 또는 Redis 장애 | 잠시 후 재조회. 오래 계속되면 Redis 연결 로그와 재구축 상태 확인 |

## 1.3 Redis

| 증상 (로그) | 원인 | 영향과 조치 |
|---|---|---|
| `redis unavailable — scores are saved to MySQL only until it recovers` | Redis 접속 불가 | 제출은 성공한다(원장 MySQL). 빈도 검사는 통과로 동작한다. 복구되면 `redis ready`가 남고 리컨실러가 따라잡는다 |
| `redis apply gave up ... reconciler will catch up` | 첫 시도와 재시도 2회 모두 실패 | 리컨실러가 맞춘다. 잦으면 Redis 지연·`REDIS_TIMEOUT_MS` 확인 |
| `redis rate limit check failed, allowing` | 빈도 검사 시간 초과 | 그 요청은 통과된다. 잦으면 Redis 지연 확인 |
| 순위표에 반영이 안 됨, 오류 로그 없음 | 시즌 센티넬(`...:ready`)이 없다 — 정산 중이거나 재구축 전 | 의도된 동작이다(5.3). 조회는 2007을 받는다. 재구축(L3) 후 반영된다 |

## 1.4 DB·잡

| 증상 | 원인 | 조치 |
|---|---|---|
| DDL 실패 errno 1205 | 운영 테이블 MDL 대기가 2초를 넘었다 (긴 트랜잭션) | 잡이 다음 주기에 상태를 다시 보고 재시도한다. 반복되면 긴 트랜잭션을 찾는다 |
| `log_ddl_audit`에 `status = 0` 행 | DDL 실행 중 세션이 끊겼다 | 대상 테이블의 실제 상태를 확인. 관리 SP는 상태를 보고 이어서 진행한다 |
| `SP_SETTLING_EXCHANGE` 1007 | settling 테이블에 다른 시즌 행이 있다 | 사람이 확인할 상황이다. 어느 시즌이 남았는지 보고 처리 |
| `SP_SETTLING_EXCHANGE` 1008 | 꺼낸 뒤 운영 파티션에 늦은 쓰기가 들어왔다 | 교환하지 않고 멈춘다. 늦은 행의 원인(시각 검사)을 확인 |
| `SP_PARTITION_DROP` 1006 | 비어 있지 않은 파티션 | 먼저 `SP_PARTITION_EXCHANGE`로 백업에 분리 |
| `... refresh failed N times in a row` (error) | API 키·랭킹 정의 재조회 연속 실패 | 기존 목록으로 동작 중이다. 폐기한 키와 빈도 한도 변경이 반영되지 않으므로 DB 연결을 확인 |

# 2. 개발 중 겪은 문제

## 2.1 SUM 첫 제출 동시 요청의 데드락

- **증상:** 같은 멤버의 SUM 첫 제출이 동시에 오면 데드락(1213).
- **원인:** `SET v = (SELECT ...)`는 SELECT가 아닌 문장의 서브쿼리라 REPEATABLE READ에서 S 락으로 읽는다. 없는 행이면 갭에 S 락이 남아 서로의 INSERT를 막았다. 또 1062로 끝난 INSERT는 상대 행에 S 락을 남겨, 이어서 FOR UPDATE로 올리면 같은 처지의 요청과 교착했다.
- **해결:** 존재 확인을 잠그지 않는 `SELECT ... INTO`로 바꾸고, 첫 INSERT가 1062면 롤백 후 처음부터 한 번 다시 한다. `TABLE_LOCK_ORDER.md`에 주의를 남겼다.

## 2.2 SUM 상한 초과가 1107이 아니라 1106으로 나옴

- **증상:** 누적 상한을 넘기려는 테스트가 1106을 받았다.
- **원인:** 테스트 기대가 틀렸다. `max_delta`는 입력만으로 판정해 트랜잭션 전에 먼저 검사하고, `score_max`는 현재 점수가 필요해 entry를 잠근 뒤 검사한다.
- **해결:** 증분을 `max_delta` 이내로 나눠 상한을 넘기는 시나리오로 고쳤다.

## 2.3 시간 단위가 SEC 이상인 랭킹의 최종 순위가 실시간 순위와 다름

- **증상:** 같은 점수, 같은 초 안의 동점자 순서가 Redis(`member_id` 순)와 정산(ms 순)에서 달랐다.
- **원인:** Redis composite는 `time_unit`으로 내림한 시간 슬롯을 쓰는데 정산 정렬은 `achieved_at`을 ms로 비교했다.
- **해결:** 정산 정렬 인덱스를 시간 슬롯 함수 키로 바꿨다 (D-57).

## 2.4 composite 정밀도 손실

- **원인:** `score × 2^time_bits`가 2^53을 넘으면 double이 하위(시간) 비트를 잃어 동점 순서가 소리 없이 틀어진다. 등록 시 비트 예산 검사(2.7)는 아직 없다.
- **해결:** composite 계산에서 안전 정수가 아니면 예외로 막는다. 응답은 성공으로 두고 리컨실러에 맡긴다.

## 2.5 RESULT 0 뒤 데이터 SELECT 실패가 성공으로 처리됨

- **원인:** SP가 `SELECT 0 AS RESULT`를 보낸 뒤 데이터 SELECT가 실패하면 핸들러의 50001이 두 번째 결과셋으로 온다. 호출부가 첫 결과셋만 보면 오류 행을 데이터로 쓴다(랭킹 정의 캐시가 비어 모든 제출이 1101).
- **해결:** `callSp`가 두 번째 결과셋의 `RESULT=50001`도 DB 오류로 던진다.

## 2.6 Windows에서 upgrade가 시작 명령 뒤 멈춤

- **원인:** 시작 명령이 띄운 백그라운드 프로세스가 출력 파이프 핸들을 물려받아, 파이프가 그 프로세스가 끝날 때까지 닫히지 않았다.
- **해결:** 명령 출력을 파이프 대신 임시 파일로 받는다 (`upgrade.ts` `runCommand`).

## 2.7 pre-commit 크리덴셜 스캔 오탐

- **증상:** 스크립트 이름 `apikey`가 크리덴셜로 탐지되어 커밋이 막혔다.
- **해결:** npm 스크립트 이름을 `credential`로 바꿨다(파일은 `src/apikey.ts` 유지). 훅을 우회(`--no-verify`)하지 않는다.

## 2.8 종료 신호가 겹치면 하트비트가 남음

- **원인:** SIGINT 뒤 SIGTERM이 오면 종료 절차가 두 번 돌고, 두 번째 `pool.end()`의 거부가 처리되지 않은 rejection으로 프로세스를 죽였다. 처리 중단 단계가 실패해도 같았다.
- **해결:** 종료 절차를 한 번만 실행하고, 처리 중단이 실패해도 하트비트 삭제·풀 종료·로그 flush는 진행한다.
