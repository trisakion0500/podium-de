# 3. 방법

- **도착률 고정(open model):** 정해진 간격으로 요청을 보내고, 지연은 예정 발송 시각부터 잰다. 서버가 느려져도 부하가 줄지 않아 지연이 과소 측정되지 않는다(coordinated omission 방지). 동시 요청이 4,000을 넘으면 보내지 않고 `drop`으로 센다.
- **처리량:** 완료된 응답 수 ÷ 경과 시간.
- **지연 지표:** 응답 시간을 빠른 순으로 줄 세웠을 때 p50(중앙값)·p95·p99는 각각 50%·95%·99%의 요청이 그 시간 안에 끝났다는 뜻이다. 평균은 소수의 느린 요청을 가리므로 꼬리 지연(p99)을 함께 본다.
- **데이터:** 멤버 10만 명 중 무작위, 요청마다 새 `requestId`(재전송 없음), 빈도 제한 없음. BEST 랭킹은 0~7,999 무작위 점수, SUM 랭킹은 +1 증분.
- **시간:** 단계당 20초, 같은 조건 3회 반복(초과 부하 탐색은 1회).
- **DB 지표:** 각 실행 전후 `SHOW GLOBAL STATUS`의 `Com_commit`, `Innodb_data_fsyncs`, `Innodb_row_lock_waits` 차이를 초당 값으로 계산.

| 시나리오 | 요청 |
|---|---|
| best | `POST /v1/rankings/{id}/scores` (BEST 랭킹) |
| sum | 같은 API (SUM 랭킹) |
| top | `GET /v1/rankings/{id}/top?size=20&memberId=` (상위 20 + 내 순위) |
| member | `GET /v1/rankings/{id}/members/{memberId}` |
| mix | best 80%, top 10%, member 10% |

# 5. 분석

## 5.1 API 1개의 병목은 Node CPU

- 2,000건/초에서 API 프로세스가 20초 동안 CPU 21.4초를 썼다. 메인 스레드 하나가 포화됐다.
- CPU 프로파일(1,500건/초)에서 사용 시간의 비중:
  - **요청 로그 약 1/3:** 콘솔과 파일에 같은 줄을 두 번 쓴다. 파일로 돌린 stdout 쓰기는 동기다. 날짜 포맷, 마스킹, 직렬화도 요청마다 한다.
  - **mysql2 약 1/6:** 그중 절반 이상은 promise 래퍼가 쿼리마다 스택 추적을 만드는 비용(`captureStackHolder`)이다.
  - 나머지는 HTTP 처리, Fastify, Redis 클라이언트에 분산되어 있다.

## 5.2 MySQL은 포화되지 않았다

- 커밋이 1,500 → 3,175건/초로 늘어도 fsync는 초당 약 1,800회로 일정했다. 동시에 커밋되는 트랜잭션들이 fsync를 나눠 쓰는 그룹 커밋이 작동했다. 커밋 수가 늘수록 커밋당 fsync 비용은 줄어든다.
- 행 잠금 대기는 모든 실행에서 0이다. 멤버별 entry 행만 잠그므로 서로 다른 멤버의 제출은 경합하지 않는다.
- API 2개에서 처리량이 2배가 아니라 1.45배(2,200 → 3,200)로 늘어난 원인은 이 측정으로 구분하지 못했다. 같은 PC에서 API 2개, MySQL, Redis, 부하 생성기가 CPU를 나눠 썼고, MySQL 프로세스 CPU는 서비스 계정이라 읽지 못했다.

## 5.3 조회는 제출보다 가볍다

- top·member는 3,000건/초에서 p99 6ms 이하다. DB를 거치지 않고(현재 시즌은 메모리 캐시, D-58) Redis Lua 한 번으로 끝나기 때문이다.

# 6. 정합성과 발견 사항

## 6.1 정합성

- 각 측정 후 MySQL `ranking_entry` 행 수와 Redis `ZCARD`가 일치했다(API 1개: 98,053, API 2개: 99,750).
- SUM 랭킹의 점수 합계가 제출 건수와 같았다(90,000건 → 합계 90,000). 증분이 빠지거나 중복 적용되지 않았다.
- `ranking_submit_key`와 `log_ranking_submit` 건수가 일치했다(588,563건).

## 6.2 과부하 직후 제출 이력 적재 지연

- 4,000건/초 직후 제출 이력이 약 3,000건 모자랐다가 몇 초 뒤 모두 채워졌다. 이력은 메모리 대기열을 거쳐 로그 DB에 비동기로 쓴다.
- 이때 프로세스가 강제 종료되면 대기 중인 이력은 잃는다. 원장(MySQL 메인 DB)과 순위에는 영향이 없다. 정상 종료는 대기열을 비운 뒤 끝난다(`drainSubmitLogs`). 로그 기록 실패가 메인 처리를 막지 않는다는 원칙(D-48)의 대가다.

## 6.3 composite 비트 예산 초과는 소리 없이 Redis 반영만 실패한다

- 첫 픽스처를 `score_max 1,000,000`, `time_bits 40`으로 만들었다. `score × 2^40`이 2^53을 넘어, 모든 제출이 성공(200)하고 MySQL에는 들어갔지만 Redis 반영은 실패했다(ERROR 로그만 남음).
- 원장은 맞고 리컨실러가 재시도하지만, 조건이 바뀌지 않으므로 계속 건너뛴다(`recovery skipped member`). 1시간 점검도 매번 불일치로 전체 스캔을 반복한다. **등록 시 비트 예산 검사(01_DESIGN 2.7)가 필요하다**는 실제 근거다.

# 7. 한계와 후속

- **단일 장비 측정:** 운영처럼 DB·Redis·API를 분리한 환경에서 다시 측정해야 실제 상한을 알 수 있다.
- **로그 비용:** 운영 로그 설정에서 콘솔 출력을 빼면 API 인스턴스당 처리량이 오를 것으로 보이나 측정하지 않았다.
- **미측정 항목:**
  - 빈도 제한이 걸린 랭킹
  - 같은 멤버에 몰리는 제출(핫 멤버)
  - 정산 중 부하 (정산 가순위는 구현됨, 미측정), 재구축 중 제출 부하가 겹칠 때
  - 장시간(분 단위 이상) 지속
- **재구축 시간:** 부하 없이 100만 명 시즌 하나를 BEST 약 6초, SUM 약 11초에 재구축했다(01_DESIGN 1.7).
- **도구:** 자체 스크립트로 측정했다. k6로 best 1,500건/초를 1회 대조해 꼬리 지연이 이 범위 안임을 확인했다([07_K6_LOAD_TEST](07_K6_LOAD_TEST.md)).

# 8. 재현 방법

로컬 개발 DB·Redis 전용이다. 운영 DB에 실행하지 않는다. 프로젝트 루트에서:

```bash
npm run build
node loadtest/load.mjs setup        # 픽스처: ranking_id 931(BEST), 932(SUM), 센티넬, API 키 2개
# 다른 터미널에서 (setup 뒤에 기동해야 새 키·랭킹을 바로 읽는다)
INSTANCE_ID=1 API_PORT=3100 node dist/api.js
INSTANCE_ID=2 API_PORT=3101 node dist/api.js
# 부하: run <best|sum|top|member|mix> <건/초> <초> [멤버 수]
LOAD_PORT=3100,3101 node loadtest/load.mjs run best 2300 20
node loadtest/load.mjs verify       # MySQL·Redis·제출 이력 건수 대조
node loadtest/load.mjs clean        # 픽스처·키 삭제
```

Windows PowerShell에서는 환경 변수를 이렇게 준다(창마다 하나씩).

```powershell
$env:INSTANCE_ID='1'; $env:API_PORT='3100'; node dist/api.js
$env:INSTANCE_ID='2'; $env:API_PORT='3101'; node dist/api.js
$env:LOAD_PORT='3100,3101'; node loadtest/load.mjs run best 2300 20
```

API 키 원문은 OS 임시 폴더(`podium-load.keys`, 소유자만 읽기)에 두고 출력하지 않는다.
